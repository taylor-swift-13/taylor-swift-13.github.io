Anthropic 的大手终于伸到了程序验证：兴奋与压力并存的时代，什么值得信任，还有哪些方向值得探索

图 2 中最容易被忽略的是蓝色的语义框。LPS 提供了连接机器代码与 Rocq 命题的执行定义：指令解码器识别二进制指令，执行语义规定寄存器、内存和程序计数器怎样变化，进程模型连接系统调用、输入输出与错误。公开源码中的 Decode.v 和 Run.v 分别展示了解码和执行关系。

用一个简化的式子概括“不出现规定的错误”这个目标：

∀x∈D, ∀e∈E, ∀s0∈Init⁡(B,x,e), ∀s,Reach⁡LPS(s0,s)⟹¬Bad⁡(s). \forall x\in D,\ \forall e\in E,\ \forall s_0\in\operatorname{Init}(B,x,e),\ \forall s,\quad \operatorname{Reach}_{\mathrm{LPS}}(s_0,s)\Longrightarrow\neg\operatorname{Bad}(s). ∀x∈D, ∀e∈E, ∀s0​∈Init(B,x,e), ∀s,ReachLPS​(s0​,s)⟹¬Bad(s).

这里 BBB 是指定二进制，DDD 是允许的输入集合，EEE 汇总允许的环境与内存布局，Reach⁡\operatorname{Reach}Reach 是 LPS 定义的可达关系，Bad⁡\operatorname{Bad}Bad 表示相应命题排除的错误。这个式子是本文示意，实际定理还区分终止、行为一致和资源前提；没有运行错误，不等于已经证明终止。

因此，它需要定义目标指令集的语法和执行规则，以及相应的系统环境；它不需要为每一种源语言重新实现整套前端语法。不同源语言编译到受支持的机器代码后，可以共享这层语义，但运行时、并发、动态加载等行为仍须落在模型的支持范围内。LPS 结构说明

二进制路线复用同一套指令和系统调用语义，代价是处理寄存器、内存布局与运行时细节。与 QCP 等围绕 C 组织符号执行和验证条件的框架相比，困难被放在不同层次；Rocq 都需要正式执行定义。结论绑定特定可执行文件，更换编译、依赖或架构后仍须重新建立对应。

2.4 要证明的命题，比“不会崩溃”更具体

主实验的输入上限为 64 MiB 以下，环境限定为受支持的单线程、静态 RISC-V/Linux 进程，并带有具体资源和环境前提。这些限制属于命题本身；更大的输入、不同架构或不同运行方式，需要相应的模型与证明。主实验范围

公开仓库区分了 **终止性质（halts）**和 行为一致性质（agreement）。前者在相应资源与环境前提下要求执行正常结束；后者比较普通构建和 sanitizer 构建的有限行为轨迹集合，并排除规定的错误。行为一致本身不排除挂起。默认 plain_halts 的内存前提，也不能读成“程序最多使用 16 GiB 内存”的结论。定理陈述文档

测试入口不触发规定错误，范围取决于指定入口、输入、构建与执行语义，不能直接推出整个库功能正确。普通构建与插桩构建行为一致，还要明确观察哪些事件、怎样比较两组行为，同样不能直接推出完整功能正确性。

入口断言总是成立，只覆盖断言写出的性质及其执行前提。程序满足完整功能规约，则还需要检查规约覆盖了哪些需求、是否忠于原始意图，以及它与真实实现的对应。

这些结论分别涉及入口安全、构建一致性、断言性质和完整功能要求。阅读时应结合各自范围：增加输入范围、改变错误定义或加强功能要求，都会改变实际需要证明的命题。

主实验以可执行检查为中心，不能直接回答解析结果、权限或系统状态是否符合完整需求。不过，安全证明可能借助复杂功能不变量，断言也可以编码功能要求。一个始终返回错误码的解析器可能很安全；若要保证它有用，规约还必须约束合法输入的接受与结果。安全、功能、终止和可用性需要分别陈述。

2.5 功能断言：LZO 与 p11-kit 的入口究竟检查什么

附录第 6 页的这段原始 C 代码同时包含控制分支、函数调用与两条断言；这里只调整换行：

r = lzo1x_1_compress(data, size, compressed, &compressed_len, wrkmem);
assert(r == LZO_E_OK);
if (compressed_len >= size) goto join;
decompressed_len = size + 1;
r = lzo1x_decompress(compressed, compressed_len,
                    decompressed, &decompressed_len, NULL);
assert(r == LZO_E_OK && decompressed_len == size);

第一条检查压缩成功；当压缩结果小于原输入时，后续分支解压并检查成功状态及还原长度。断言失败会进入中止路径，因而排除 crash 的证明也覆盖这些要求。在二进制中，两条断言编成跳向 abort 处理程序的分支，证明按确切指令地址分析并排除这些分支。附录还介绍了管理智能卡与密码硬件的 p11-kit：其配置词法分析器在识别 PEM 块时，断言块长度不超过输入缓冲区末尾；这类维护者写在入口中的约束，同样成为证明需要排除的失败分支。附录第 6 页代码与说明

这个例子纠正了“安全性完全没有功能内容”的笼统说法。入口断言可以要求算法返回成功并恢复正确长度。不过，这段代码没有比较解压字节与原输入；仅依据这些断言，不能将结论扩大成完整的逐字节往返正确性。进一步的功能保证，要落实到完整入口、实际 spec 和已完成的定理上。

Python 解释器的完整实验条件与变异检验

解释器实验采用 safe Rust、Verus 和 Z3，按基于 λπ 的形式语义完成 17 个层次的证明。结论约束返回结果；与 CPython 的对应由测试检验。作者另外向早期版本注入七个错误，其中五个通过了随机测试，七个都使证明失败。选择 Verus 而非 Lean 是实践偏好，也用于检验模型适应不同形式系统的能力，并非技术上只能如此。这里是源码层的 Hoare 风格验证：以 requires、ensures 与循环不变量等契约表达要求，再由 Verus 调用 Z3 证明代码满足契约，与主实验的 Rocq 二进制路线不同。附录第 2–3 页

这组结果说明证明可能发现测试遗漏的错误，同时也展示了信任边界：实现与形式模型之间有证明，形式模型与 CPython 之间有经验比较。若形式语义漏掉了需求，前一项证明仍可能全部成立。人工注入错误的结果也应按这七个案例理解，不能外推为所有缺陷的检出率。

2.7 主实验怎样使用 Rocq，是否需要现成验证器与 SMT

公开主实验的检查流程以 Rocq 为核心：给定二进制映像与固定命题，编译代理提交的证明，再检查假设。检查镜像包含 Rocq、LPS 及相关库，并不携带额外的证明自动化；编译、sanitizer 插桩、映像提取和生成脚本仍然参与整个流程。检查环境

这条主线没有把“由现成源码验证器生成 VC，再交给外部 SMT”作为说明中的核心步骤。另一项 Rust 解释器实验则使用 Verus 与 Z3。因此，“Rocq 主实验的证明检查不以外部 SMT 为核心”与“全文所有实验都不用 SMT”是两个不同说法。附录第 3 页

人类设计宏观任务、检查接口和信任边界，模型完成繁重形式化与证明，是这项工作的组织方式。它减少了预先为每个困难设计专用求解器的要求，但仍依赖 Rocq、编译器、sanitizer 和生成脚本。强模型能直接面对正式语义时，哪些额外自动化仍有价值，需要用实际收益回答。

3. 沿真实 Rocq 代码看：到底定义了什么、证明了什么

以下核对固定到公开证明仓库的 98e995d4 与 LPS 的 f1006fe8，避免将后续版本混在一起。代码片段分别注明原样节选与解释性示意；定义存在、命题被证明、命题适用于部署程序，是三个需要分别核对的状态。

下面沿一条可以追踪的源码链阅读：Statements.asan_agrees → Shapes.agrees_in → run_scfg 与 error_free → cJSON 的共享轨迹规约 → 已发表的 Proof.v。所有代码均来自固定快照；完整定义与证明正文按原码展示或仅调整换行，结构节选另行标明。

3.1 真实 spec：cJSON 的两条 Rocq 定义

projects/cjson/cjson_read_fuzzer/Statements.v 中有以下定义，原样节选并调整换行：

Definition plain_halts : Prop :=
  halts_within_budget
    Budgets.Standard.lim_source
    Exits.ok_or_refused
    Images.plain.

Definition asan_agrees : Prop :=
  agrees_in
    Env.alloc_forced_only
    Budgets.Asan.lim_source
    Budgets.Asan.lim_target
    Images.plain Images.asan.

这里的 Prop 表明它们是命题。第一条把终止模板应用于普通二进制映像，第二条把无错误且行为一致的模板应用于普通构建和 ASan 构建。具体含义取决于模板、参数和映像；两行调用很短，并不意味着完整定义或证明也很短。

在固定版本中，plain_halts 仍是开放目标（open）：它要求在资源与环境前提下，以允许状态终止。asan_agrees 已证明（proved）：它要求两个构建无规定错误，且有限可观察行为集合相同。

ubsan_agrees 与 asan_ubsan_agrees 也已证明，分别对应相应插桩构建的一致性与无错误要求。关于输入分布的概率界，以及识别一致输入的可判定性命题，仍是开放目标。

上述证明状态来自该入口的 README。其中还说明，入口会解析、打印和压缩 JSON 文本，但输出被释放，没有进一步比较内容。因此，这个例子的证明不能读成 JSON 解析与输出的完整功能正确性；已经完成的一致性证明也不能自动升级成尚未完成的终止证明。

这是读取项目结果时很有用的一种顺序：先找具体入口，再看陈述，然后核对证明状态。仅看到一个命题写成 Definition ... : Prop，不能断言它已经被证完。即使入口调用了复杂算法，它是否有功能保证，仍取决于驱动程序实际观察了什么。

3.2 映像不是抽象函数，而是指定 ELF 的加载结果

Images.v 给普通构建的定义是：

Definition plain : Image :=
  mkImage
    Plain.M.loaded_segments
    Plain.M.init_pc
    Plain.M.phdrs.

三个参数分别来自该二进制的可加载段、入口地址和程序头信息。底层段数据由 elf-snapshot 在构建时生成；harness.yaml 则记录源版本、构建和二进制 SHA-256。映像还要检查良构性，排除“根本没有合法启动状态，所以全称命题空泛成立”的情况。

这个驱动会读取输入文件并调用 fuzz 入口。参数错误、文件不可读、头部不完整或文件达到 64 MiB 时，可以直接返回状态 2。允许的正常退出集合包含 0 和 2，因此“退出状态合法”不要求每个文件都成功进入库函数。各构建还固定了部分环境函数的结果，例如 getenv() 返回空指针、getpid() 返回 1。这些细节也属于被验证程序的身份。入口与驱动说明

这也解释了为什么证明必须绑定软件产物。模型证明的是这些段里的指令及其允许的运行环境；源代码仓库里的相同文件名，不能替代二进制身份。驱动拒绝输入本身可以是正确行为，但要确认它没有把原本需要处理的正常输入排除掉。

3.3 完整目标：量词、预算、三个结论与单独的终止义务

Shapes.v 的 agrees_in 完整定义如下，保留全部量词、前提与三个结论：

Definition agrees_in (env : SpuriousCfg) (lim_plain lim_san : Z) (plain san :
  Image) : Prop :=
  forall (en_plain en_san : ExecEntry) (inp : ProcInput),
    valid_entry plain en_plain inp ->
    valid_entry san en_san inp ->
    valid_input inp ->
    ~ run_scfg_budget_refused env plain lim_plain en_plain inp ->
    error_free (run_scfg env plain lim_plain en_plain inp)
    /\ error_free (run_scfg env san lim_san en_san inp)
    /\ trace_equiv (bh_traces (run_scfg env plain lim_plain en_plain inp))
                   (bh_traces (run_scfg env san lim_san en_san inp)).

外层对两个构建的启动布局和进程输入分别全称量化。进程输入包括参数、环境变量、初始文件、标准输入等；启动布局包括栈、堆起点和相关随机字节。两个构建的布局不必相同。前提成立后，要得到普通构建无错误、插桩构建无错误，以及两者有限轨迹集合相同。

逐行读这段 Rocq：forall 不是抽取几个测试样本，而是固定映像下所有合法进程输入与两个独立的启动布局；连续的 -> 引入必须满足的前提；~ run_scfg_budget_refused ... 是对普通构建运行的预算前提；最后的 /\ 把三个义务合取。第一项已经直接要求普通构建无错误，并非只靠 ASan 的检测能力推出来。第三项比较两组可能的有限轨迹，而不是某次运行的单条输出。

run_scfg 的参数依次给出环境失败策略、二进制映像、预算、启动布局和输入。cJSON 的 ASan 一致性目标采用普通构建 2 GiB、插桩构建 512 GiB 的预算；普通终止目标另用 16 GiB。alloc_forced_only 要求内存请求只在预算耗尽或找不到可用地址范围时失败，其他种类的请求仍可能失败。它们是不同命题的参数，不能混成一个统一资源保证。参数与模板定义

真实 spec 的复杂性主要藏在这里。用中文概括为“所有输入都不崩溃”很方便，但允许哪些环境失败、预算条件放在哪个构建上、轨迹怎样比较，都会改变证明难度和结论范围。检查这些前提，比单看定理名称更能判断保证是否适用。

再对照同文件中的终止模板。这里不是 error_free，而是另一个谓词 must_exit_in_scfg：

Definition halts_within_budget (lim : Z) (allowed : list word) (img : Image) :
  Prop :=
  forall (en : ExecEntry) (inp : ProcInput),
    valid_entry img en inp ->
    valid_input inp ->
    ~ run_scfg_budget_refused forced_only_cfg img lim en inp ->
    must_exit_in_scfg forced_only_cfg allowed img lim en inp.

它要求每一条允许执行最终正常退出，且状态属于 allowed；因而同时排除无限执行、卡住、错误和信号终止。forced_only_cfg 还禁止环境无缘无故拒绝请求，比一致性目标的 alloc_forced_only 更强。代入 cJSON 的 plain_halts 后，预算是 16 GiB，允许退出状态为 0 或 2；这个目标在固定 README 中仍为 open，不能因下面的一致性定理已经有证明就宣称它也成立。

ASan 没有任意环境失败下的同类 halts_may_fail 目标：运行时的启动地址空间预留若被拒绝，会刻意等待不结束。这个反例说明，环境前提是程序行为的一部分，不是可以省略的注脚。

3.4 为什么三个结论缺一不可：轨迹一致可能掩盖 crash 与挂起

附录先要求 ASan 构建无错误，再比较它与普通构建的可观察行为，最后单独排除普通构建的错误。观察对象包括标准输入读取、标准输出和错误输出写入、退出状态或终止信号，以及最终文件系统；性能不在这个比较范围内。错误则包括故障、主动中止和语义未覆盖的行为。附录第 1–2 页

这个拆分有实际原因：有限轨迹本身没有单独记录 crash，一个程序发生错误、另一个进入不再产生事件的死循环，可能仍具有相同的有限观察。因此，不能只靠轨迹相同，就把一个构建的无错误性质传给另一个。§3.3 的公开模板把两个 error_free 与轨迹一致性明确合在同一命题中，但终止仍是另外的目标。

这是阅读“一致性证明”时最应检查的细节之一：一致的是哪些观察，错误与不终止怎样进入定义，结论是否足够强。一个关系名称叫 equivalence，并不意味着它自动保留所有关心的性质。

3.6 一步如何执行，系统调用为什么是非确定的

Definition syscall_spec

  dispatch spec_table.

一个系统调用规约可以允许多个结果，例如读取部分可用字节，或在所选环境允许时返回失败。实际效果包括返回值、写入内存的字节，以及映射、清零等变化；进程转换关系再将允许的效果应用到状态。这里需要证明的是所有许可分支，而非一次解释器运行所选择的分支。系统调用效果

  → 解释指令，更新状态
  → 系统调用：选择许可结果
  → 产生下一状态与可观察事件

这条流程在源码中被拆成机器步进、系统调用处理和 sstep 转换关系；最终的运行行为则收集任意有限步数所能产生的轨迹。步进与运行关系

3.7 整体行为是什么，证明文件又交付什么

3.8 crash 在 Rocq 中是什么：错误单步、可达性和否定命题

LPS 没有一个理解所有源码 bug 的通用检测器。它先规定指令、访存和系统调用怎样执行，再规定哪些结果进入错误分支，最后提出错误不可达的命题。下面沿固定版本的源码展开这条链。

机器层的 machine_result 区分正常结果 MachineOk、真实执行故障 MachineFault 和语义未支持的 MachineUnmodeled。例如，访存解释需要读取的字节不存在，或存储范围含不可写字节，便产生故障；取指失败时，还会区分真实不可执行地址与模型自身无法解释的情形。机器结果与访存解释

进程层的 sstep 是一步转换关系。以下是 Run.v 的实际故障构造子，作为归纳定义的一部分原样节选，并非独立定义：

| sstep_instr_fault : forall ms model,
    m_halted model = None ->
    ms_svc_pending ms = None ->
    mi_account_step ms model = MachineFault ->
    sstep (mkCfg ms model) [] SError

三个箭头前提分别要求进程尚未正常退出、当前没有待处理系统调用，以及本次机器步进确实产生 MachineFault；满足后，结论就是存在一步到达 SError。相邻的 sstep_instr_unmodeled 规则把 MachineUnmodeled 也送到 SError。系统调用另有规则，返回错误码的调用仍可能正常执行，不能一概视为 crash。

接着，star 连接零步或多步正常转换，reaches_error 的定义把“某条执行能出错”精确写成存在量词：

Definition reaches_error (c0 : config) : Prop :=
  exists tr c evs, star c0 tr c /\ sstep c evs SError.

exists tr c evs 提供反例执行的见证：从初态 c0 沿轨迹 tr 到达 c，再由一步 sstep 进入错误。只要存在一个这样的见证，无错误命题就不成立；证明无错误要排除全部见证。

带环境失败策略的实际运行定义如下。它由映像与启动布局构造初始配置，再把错误可达性放进 behavior 记录：

Definition run_scfg (cfg : SpuriousCfg) (img : Image) (lim : Z) (en : ExecEntry)
    (inp : ProcInput) : behavior :=
  match img, en with
  | mkImage segs pc ph, mkEntry sp brk0 mbase rnd =>
    let c0 := init_config segs pc ph sp brk0 mbase rnd lim inp in
    {| bh_traces := obs_trace_cfg segs cfg c0;
       bh_errors := reaches_error_cfg segs cfg c0;
       bh_all_errors := all_traces_error_cfg segs cfg c0;
       bh_unmodeled := reaches_unmodeled_cfg segs cfg c0 |}
  end.

这里 _cfg 版本在 SpuriousCfg 指定的许可分支上建立同样的可达关系。上层 agrees_in 使用的正是它。在 Equivalence.v 中，无错误的完整短定义是：

Definition error_free (b : behavior)
  : Prop := ~ bh_errors b.

所以真正的逻辑链是：合法输入和布局 → 初始配置 → 许可单步关系 → 是否存在到达错误的有限路径 → 该存在命题的否定。这不是穷举运行所有输入，而是对这些定义建立归纳、不变量、模拟关系和组合证明。进程转换与运行定义、无错误定义

ASan 本身也是这些机器指令的一部分。证明会跟随地址检查、影子内存读取和条件分支；如果检查失败，后续报告与中止路径就成为必须排除的执行。语义并不是在每一步直接调用一个名叫“内存安全”的抽象判断。

中止的具体编码还取决于所用命题族。默认设置与显式建模 abort 的设置不同；后者可以产生 KillEv，而不经过 SError。相应的 _abort_modelled 安全目标采用 error_free_unkilled，另外禁止信号终止。因此，“不可到达 SError”与“不会因信号终止”需要按具体定义组合，不能把所有 crash 都想成同一个硬件异常。中止与信号终止的定义

这条链也精确定位了形式化错误的后果：如果一个本应失败的真实操作，在语义中被写成正常后继，证明器就可能正确地证明这个错误模型中的不可达性。真实复现仍能确认一个 bug；从不可达性推导真实程序无错误，则需要这条执行与错误分类的对应可靠。

3.9 真实证明实例：共享轨迹规约、三个子目标与最终 Qed

附录提到代理往往先写短规约，再分别把普通构建和插桩构建与它联系起来。cJSON 的公开代码正好能把这个过程展开。这里的中间规约不是自然语言“JSON 正确”，而是可观察轨迹集合；ShapeAlg.v 定义：

Definition TSet := list event -> Prop.

一个 TSet 回答某条有限事件序列是否属于该规约。ShapeSpec.v 的 t_body 根据输入头部决定拒绝还是调用，并描述驱动输出；下面保留完整定义，只调整换行并省去导出注释标记：

Fixpoint zero_lines (calls : nat) : list byte :=
  match calls with
  | O => []
  | S k => Z_to_bv 8 48 :: Z_to_bv 8 10 :: zero_lines k
  end.

Definition MAX_INPUT : Z := 67108864%Z.

Definition t_body (data : list byte) (fs : Fs.Fs) : TSet :=
  let len := length data in
  if (MAX_INPUT <=? Z.of_nat len)%Z then t_die msg_refused fs
  else if (len <? 6)%nat then t_die msg_short fs
  else
    let b0 := bv_unsigned (nth 0 data (Z_to_bv 8 0)) in
    let b1 := bv_unsigned (nth 1 data (Z_to_bv 8 0)) in
    let b2 := bv_unsigned (nth 2 data (Z_to_bv 8 0)) in
    let cfg := (b0 + 256 * b1)%Z in
    let config_len := Z.to_nat (cfg mod 32768) in
    if (len <? 6 + config_len)%nat then t_die msg_overrun fs
    else
      let calls := match config_len with O => 1%nat | _ => S (Z.to_nat (b2 mod 4))
        end in
      t_emit (W 1 (zero_lines calls)) (t_exit (exit_code 0) fs).

67108864 = 2^26，即 64 MiB。少于 6 字节的头部、配置长度越过输入末尾、输入达到上限，都会走 t_die；它定义为向文件描述符 2 写入对应错误消息，再以状态 2 退出。合法头部确定调用次数 calls：没有配置时为 1，否则为 1–4。zero_lines 生成相应数量的 0\n，W 1 将字节写到标准输出，最后以状态 0 退出并带上文件系统状态 fs。t_emit 同时包含有限前缀，符合前述轨迹集合的读法。实际中间规约、轨迹组合定义

这就具体回答了“规约长什么样”：它能精确规定 CLI 与 fuzz driver 的可观察行为，但这段规约没有把 JSON 解析结果写成数学树，也没有要求打印内容等于某个标准 JSON 结果。因为驱动释放内部输出而不比较它，内部执行分析再繁重，最终约束仍要以这些观察为准。

中间规约又如何与真正的机器单步连接，而不是另写一套互不相干的模型？ShapeAlg.v 在固定 segs 的 Section 中给出以下完整定义，ACFG 是证明所用环境策略：

Definition node_ok (c : config) (I : Type)
    (evs : I -> list event) (nx : I -> config) : Prop :=
  (forall i, sstep_cfg segs ACFG c (evs i) (SNext (nx i)))
  /\ (forall e st, sstep_cfg segs ACFG c e st -> exists i, e = evs i /\ st = SNext
    (nx i)).

第一个 forall 要求索引集合 I 列出的每种事件与后继，都是实际 sstep_cfg 允许的正常一步；第二个 forall 反过来要求任意实际一步都在该索引描述中，而且结果是 SNext。因此，不能只挑几条有利路径、遗漏另一条可达 SError 的路径。下层 realizes 归纳证明再把这些单步与后继证明组合起来。连接规约与单步的定义

证明怎样利用这个中间层？ATop.v 中以下完整引理把两个运行联系到同一个 T；只调整换行前后的空白，使用该文件已有的 imports 与局部记号：

Theorem shape_strong_equiv_sef_AS :
  forall source_segs rpc rph rsp rbrk rmb rrnd (rlim : Z)
         target_segs apc aph asp abrk amb arnd (alim : Z)
         (T : TSet) (inp : ProcInput),
  realizes source_segs (init_config source_segs rpc rph rsp rbrk rmb rrnd rlim
    inp) T ->
  AS.SpinAlg.srealizes target_segs (init_config target_segs apc aph asp abrk amb
    arnd alim inp) T ->
  error_free (run_scfg ACFG (mkImage source_segs rpc rph) rlim (mkEntry rsp rbrk
    rmb rrnd) inp)
  /\ error_free (run_scfg ACFG (mkImage target_segs apc aph) alim (mkEntry asp
    abrk amb arnd) inp)
  /\ trace_equiv (bh_traces (run_scfg ACFG (mkImage source_segs rpc rph) rlim
    (mkEntry rsp rbrk rmb rrnd) inp))
                 (bh_traces (run_scfg ACFG (mkImage target_segs apc aph) alim
                   (mkEntry asp abrk amb arnd) inp)).
Proof.
  intros source_segs rpc rph rsp rbrk rmb rrnd rlim target_segs apc aph asp abrk
    amb arnd alim T inp Hsource Htarget.
  split; [| split].
  - cbn. eapply realizes_no_error; exact Hsource.
  - cbn. eapply AS.SpinAlg.srealizes_no_error; exact Htarget.
  - intro tr. cbn.
    rewrite (realizes_obs_iff source_segs _ T Hsource tr).
    rewrite (AS.SpinAlg.srealizes_obs_iff target_segs _ T Htarget tr).

4.5 专家怎样看这些证明：短规约、冗长展开与抽象能力

附录中的专家观察是，代理经常先写一个描述输出的短规约，再把两个构建分别与它联系起来；这类规约的中位数约 110 行，对应程序机器代码中位数约 86 KB，其中驱动实际涉及约 20%–50%。证明过程却反复展开寄存器、整数转换、地址互异、栈内容与各分支。代理也使用了 framing、布局无关推理和分配器抽象，但使用并不一致，证明规模改善仍有限。附录将更复杂程序上的规模扩展列为开放问题，并以 MachCSL 等其他代理验证项目遇到的复杂度问题，讨论建立更好模块抽象的必要性。后续问题包括：合适抽象是否需要专家证明工程师指导，还是可以提炼通用原则，让代理自行发现支持扩展的抽象。附录第 4–5 页

短规约的出现值得关注，但“两个实现都满足同一规约”本身并不足以推出两者行为一致。例如，一个程序输出 0，另一个输出 1，两者都满足“输出非负”。中间规约必须具有足够的区分能力，或配合更强的对应定理。最终应检查实际证明出的关系，不能只看规约长度。

冗长证明一旦通过同一目标的可靠检查，其逻辑效力不因写法而降低；抽象的价值主要体现在后续扩展、复用、调试和成本。能否自动找到合适的模块边界，比是否模仿人类的证明风格更值得验证。

5. 什么值得信任：从证明检查到现实对应

5.1 证明文本可以不逐行阅读，信任基础仍要具体

公开检查流程会核对二进制哈希，从源文件编译证明，并生成独立包装定义，要求提交的证明具有指定陈述的类型；随后检查 Print Assumptions。仓库列出允许使用的公理，拒绝额外假设和未完成证明。默认检查使用 Rocq 内核；rocqchk 是可选的第二次检查。证明检查流程

信任基础还包括 ELF 到内存映像的工具、读取映像的插件、检查包装和假设解析程序，以及实际使用的 LPS 定义。检查器确认一个形式命题有证明；这些外围环节决定该命题是否对应预定的验证目标。信任基础文档

原文脚注还把运行证明检查器所依赖的硬件、操作系统与 OCaml 编译器纳入信任基础。因此，“信任 Rocq 内核”也包含让这份内核实现正确运行的执行环境。原文脚注 5

从需求走到部署，需要分别核对几个环节。需求与规约要检查命题、前提、输出与错误定义是否包含实际需求；执行语义要检查指令、系统调用、启动与环境模型是否忠于目标平台；软件产物要用哈希、映像、版本与依赖确认指向的确实是这份二进制。

证明检查要核对内核、允许公理、独立包装与审计，排除额外假设和错误目标；实际部署还要满足定理要求的架构、链接方式、并发与资源条件。

这些环节形成了从需求到部署的证据链。证明检查主要约束证明是否成立，二进制哈希帮助固定软件产物；它们不能单独完成需求、语义与部署条件的核对。判断一份证明能否服务于真实系统，需要把这些环节接起来。

可靠检查链允许生成模型犯错，却不能替代正确目标：弱化性质、排除失败输入或更换程序都可能使证明轻易成立。因此，目标固定、产物固定与假设审计同样重要。

LPS 与真实机器的对应仍是一项重信任义务。对找漏洞，可以先采用经过测试、范围明确的模型，再真实重放反例；这种工程判断不能直接升级为无错误保证。

5.2 机器模型的缺口会成为结论的边界

LPS 的范围说明列出了单线程、静态可执行文件、信号处理及文件系统等限制，也列出了若干未检查的外部假设。文档特别说明：某些模型中过宽的非确定行为，会影响两个程序行为集合的等价比较；模型内的等价不一定自动转移到真实系统。LPS 范围与已知缺口

原文特别指出，实验使用静态链接 musl 的 RISC-V 程序，而常见部署可能是 x86 或 ARM、动态链接 glibc；已有证明不会自动转移过去。实验也没有验证每个库的全部入口，即使所有 fuzz 入口都验证，仍不等于覆盖所有库代码与调用情境。调用者若违反 API 使用条件，还可能在库外造成内存破坏，因此调用者义务同样需要写清。原文的部署与调用边界

对全称安全性质，保守过近似可能足够；对行为集合相等，两边增加模型特有行为可能改变结论。语义的适用性取决于目标性质。共享语义既会传播错误，也会集中收益，因此需要版本化的适用范围、差分记录、参考语义对应与变更后的重查范围。

5.3 直接验证二进制，仍然需要跨越模型与现实

附录解释，直接把测试翻译成 Rocq 可能引入翻译错误，源码解释器也可能偏离实际编译结果，因此项目选择解释编译后的二进制。附录第 1–2 页

源码转换需要连接原程序与模型，二进制验证需要连接机器模型与平台。两条路线都应保留所关心的正常返回、错误和发散；差分测试能发现偏差，严格保证还需对应论证。静默丢弃错误执行，会让模型比真实程序更安全。

5.4 自动修补以后，被证明的程序已经改变

原文允许 Claude 修补证明过程中发现的问题，再为新程序重新生成目标；脚注同时讨论了修改程序以迎合目标的风险，并介绍了补丁惩罚、行为变化奖励和日志审计。原文脚注 6

公开发布的材料也有筛选：原文说明提供不需修补的部分完整证明、其他任务的陈述及可信组件，并暂不发布可能揭示未修复漏洞的证明。因此，公开仓库不是完整实验结果的逐项清单。原文的发布范围

6. 找 crash、证明无 crash 与完整内存安全：从一次越界写说起

6.1 到底在找什么 bug：先看入口怎样失败

主实验把库、fuzz 驱动与插桩运行时编译成程序，寻找能使这个程序进入规定错误的输入。失败可能来自普通程序自身的故障，也可能来自 ASan 报告后中止，或入口中的断言失败。模型不支持的行为也被纳入证明要排除的错误，但单凭模型无法继续执行，还不能确认真实程序有漏洞；需要诊断并重放。

作者报告，针对数百个入口的证明尝试发现了数百个 bug，其中一些在既有万亿次量级的测试后仍未暴露。原文将常见 fuzzer 的输入上限描述为约 1 MB，用来解释大输入为何可能成为测试盲区；这不是所有 fuzzing 配置的固定上限。原文的发现规模与测试背景

原文举出的一个例子是：某个解压器只有在约 20 MB、布局特殊的输入下才出现计数器下溢，进而发生越界写。这说明证明过程中寻找输入，可以触及常规 fuzzing 很难碰到的组合条件。原文主实验的最终目标是修补后完成指定入口的无 crash 证明；寻找漏洞也是即使未能证完仍可交付的成果。原文的漏洞发现与实验目标

原文还列出其他触发条件：图像解码器越界读需要约 64 MB 输入与超过 2 GB 内存；另一处越界读依赖同一文件的两个句柄之间的特定调用历史；libexpat 的 CVE-2026-56132 则由深层嵌套输入触发。此外，代理还发现不一定导致 crash 的文件加载限制失效。这些案例分别涉及输入规模、调用历史、递归结构与权限逻辑，不能都简化成一次普通数组越界。原文的缺陷案例

这里的 crash 是检查程序的失败信号，不能与所有软件错误画等号。 ASan 可以把某些原本暂时不崩溃的内存错误变成报告与中止；维护者也可以用断言把算法要求变成失败分支。§2.5 的 LZO 示例检查成功状态与还原长度，就是后一种情况。入口没有观察的功能要求，不会仅因为“入口不崩溃”就自动得到验证。

对找 bug 的目标，最有说服力的交付物是能够真实复现、并违反预期契约的输入及执行过程。证明失败只是线索；证明成功和漏洞复现则是两种不同的成果。报告结果时，把它们分别计数，能够更准确地体现这条路线的价值。

6.2 ASan 做了什么：越过箱子边界，不一定撞到仓库的墙

可以把进程的可访问地址空间想成仓库，把一次分配得到的缓冲区想成箱子。操作系统的页级保护通常不会为每个小对象单独立墙：写出了箱子，却还在可写的仓库区域里，程序可能暂时正常运行，只是已经破坏了数据。

ASan 通过编译时插桩与运行时库，为许多内存访问增加检查，并用影子内存记录地址是否允许访问。可以把它理解为在部分边界和失效区域布置警报。某次访问命中禁用区域，便报告错误并通常中止程序；这些机制并不等于完整跟踪所有对象归属与语言层面的内存合法性。ASan 的组成与工作方式

例如，假设驱动分配了 16 字节的堆缓冲区 p，输入控制索引 i，随后调用这个解释性示例；它不是论文项目中的原码：

void put(char *p, size_t i) {
    p[i] = 1;
}

i == 16 时，尝试写入的是第 17 个字节。普通构建可能破坏邻近数据而没有立即崩溃；在 ASan 构建中，如果目标地址被标记为禁用区域，相应检查会报告越界并中止。于是，一个原本可能静默的内存错误，被转换成 fuzz 驱动与无错误命题能够观察到的失败。

输入控制索引
  → 执行一次写入
  → ASan 检查目标地址
  → 命中禁用区域，报告并中止

对某个输入运行一次，能够发现这次执行中的报告；形式证明进一步尝试排除前提范围内所有执行的这种失败。两者使用同一类可执行检查，但覆盖的量词不同。证明的是指定二进制中实际存在的检查，而非任意版本、任意配置的 sanitizer 都不可能报告。

6.3 三种结论的量词和依据不同

找到并确认一个 crash，需要一个输入及相应环境，在真实目标上复现规定失败，并确认违反预期契约；它不回答其他输入是否安全。

指定插桩构建无 crash，需要排除前提允许的全部执行中的规定错误，并建立模型与真实执行的对应；它不等于所有 sanitizer 都不会报告，也不等于所有内存错误都不存在。

普通构建无 crash，直接排除该二进制在允许执行中所定义的故障与中止等错误；仅凭这一点，不能推出没有静默内存破坏、没有错误输出或一定终止。

完整内存安全，要求对明确的内存安全定义，排除范围内全部执行的相关违规，例如对象边界和生命周期违规。它同样不自动保证全部功能正确，也不排除主动中止或挂起。

这些目标中的“全部”同时受入口、输入、内存布局、环境响应和资源前提约束；“完整内存安全”也必须先说明采用什么语言或机器层定义。无 crash 与内存安全不是简单的线性包含关系：程序可以内存安全却触发失败断言，也可以越界写却暂时不崩溃。

公开的 agrees_in 并非只要求 ASan 不报告。它还直接要求普通构建无模型错误。将其结论缩写，结构是：

ErrorFree⁡M(P)∧ErrorFree⁡M(S)∧Traces⁡M(P)=Traces⁡M(S). \begin{aligned} &\operatorname{ErrorFree}_{M}(P)\\ &\quad\land\operatorname{ErrorFree}_{M}(S)\\ &\quad\land\operatorname{Traces}_{M}(P) =\operatorname{Traces}_{M}(S). \end{aligned} ​ErrorFreeM​(P)∧ErrorFreeM​(S)∧TracesM​(P)=TracesM​(S).​

这里 PPP 是普通二进制，SSS 是指定插桩二进制，MMM 是形式语义；外层量词和前提见 §3.3。既然普通构建的无错误性本身就在证明目标中，它不必通过“ASan 能捕获所有 crash”来间接获得。实际命题模板

如果只有“ASan 从不报告”这一结论，却要推出“任何内存错误都不存在”，则需要额外证明：每一种目标内存错误都会在相应插桩执行中被报告。现有 ASan 不提供这样的完整覆盖。普通构建无模型错误，也不能补上模型并未定义为错误的对象归属或子对象边界违规。cJSON 陈述中的覆盖限制

评价这项工作时，应分别承认三类价值：真实复现的缺陷、指定语义与前提下的无错误证明，以及进一步建立的功能或内存安全性质。把第一类成果贬成“没有完整保证所以没用”，会低估找漏洞的工程价值；把第二类成果直接写成完整内存安全，又会扩大它的证明范围。

6.4 形式化不可信，会影响哪一条结论

继续使用仓库的比喻：形式语义像一份描述通道、边界和警报器的地图。依据地图找到可疑位置，再到真实仓库确认确实出错，这个发现不因地图其他地方画错而失效。反过来，仅在地图上证明所有路线都安全，结论能否适用于仓库，就取决于地图是否保留了真实可能发生的危险。

找 bug：
  模型提供候选输入
  → 真实目标复现失败

提供保证：
  模型内完成全称证明
  ＋ 模型与真实执行的可靠对应
  → 前提范围内排除规定错误

因此，错误或尚未充分验证的形式化，可能使寻找漏洞的过程遗漏真实错误，也可能产生无法复现的线索；但一个已经在真实目标上复现并确认的 bug，仍然有效。对于“所有允许执行都安全”，若模型漏掉真实执行、把错误当作正常结果，或错误处理了运行环境，则模型内证明不足以支持现实中的全称保证。

这里需要的是适合目标性质的语义对应。对全称安全性质，保守覆盖真实执行可以足够，并不要求模型中的每条行为都真实可发生；但不能悄悄丢掉真实错误。语义的依据可以由差分执行、独立审计和与参考模型的对应证明加强；通常的有限样本测试不能完成对所有执行的对应论证。§5.2 讨论了过近似对安全性和行为等价的不同影响。

还应区分语义与检查器：如果只有语义偏离现实，而 Rocq 检查链可靠，那么已检查的形式命题仍然成立，缺少的是将它应用到现实的依据。若检查链本身也不可靠，连模型内的证明结论都需要重新核验。项目的信任基础

“形式化需要信任”不意味着只能凭感觉接受，也不意味着所有结果一并作废。更有用的做法是明确哪部分尚未建立对应、哪些已复现的发现不受影响、哪些无错误保证仍带着假设。找漏洞允许先采用有用但不完美的地图；提供保证则要交代地图与现实之间的证据。

6.5 ASan 会漏掉什么：地址可访问，不代表访问合法

ASan 的内存访问检查可能遗漏几类情况。对象内部越界，例如数组成员越界覆盖同一结构体的后续成员，默认检查未必区分内部边界。错误访问落入另一个活对象时，目标地址仍可访问，ASan 未必知道指针本应属于另一个对象。未插桩代码中的普通访问则可能没有相应检查；拦截器可以覆盖部分操作，但不能视为全面覆盖。

逻辑有效长度也是另一种边界：分配 1,024 字节、只有前 64 字节有效时，读取第 100 字节可能不报错，需要长度不变量或相应标注。未初始化值的使用主要由 MemorySanitizer 检查；整数溢出、非法移位等未定义行为需要相应 UBSan 配置；数据竞争由 ThreadSanitizer 等检查，而主实验限定单线程。

功能或权限错误，例如输出内容错误、遗漏权限检查，通常还需要功能规约或断言提供判断标准。通用 sanitizer 不会自动知道业务预期。

这些情形既包括 ASan 内存检查本身的缺口，也包括它不负责的其他性质。公开 cJSON 命题明确列出“访问落入另一个活对象”和“未插桩代码”两类限制。项目中的明确说明 容器内部逻辑边界可以通过专门标注增强检查；没有标注时，不能自动把分配边界理解为有效数据边界。ASan 容器检查说明

一个更容易看见的对象内部越界例子如下，同样是解释性示例：

struct S {
    char data[8];
    int allowed;
};

void put_member(struct S *s, int i) {
    s->data[i] = 1;
}

在常见布局下，i == 8 可能写到 allowed 的字节。它已经越过 data 的数组边界，却仍处于整个结构体对象内部；默认 ASan 可能不报警。用箱子比喻，这相当于破坏了箱子内部的隔间，但没有碰到外侧警报。某些 UBSan 边界检查或额外布局插桩可以覆盖部分此类情况，不能据此宣称所有内部越界都被排除。ASan 开发者对内部越界的说明

其他 sanitizer 也各有目标：MemorySanitizer 关注未初始化值的使用，UBSan 覆盖启用的未定义行为检查，ThreadSanitizer 检测数据竞争。启用了某个工具，不等于已经启用这个工具族里的全部检查；全部检查都通过，也不会自动生成业务功能要求。

最需要避免的跳跃，是从“警报没有响”推到“所有错误都不存在”。证明能把指定警报在有限样本上的沉默，提升为前提范围内所有执行都不触发它；证明的量词变强了，警报本身的检测边界仍然存在。要进一步获得完整内存安全或功能正确性，就要把那些遗漏的要求真正放进模型与命题。

6.6 覆盖了哪些 RTE：机器故障不等于源语言的全部未定义行为

主实验中的失败信号包含几类来源。首先，LPS 把访问未映射地址、写入不可写区域、执行架构定义的非法指令等情况判为机器故障。其次，ASan 的已插入检查可以在发现相应内存错误后报告并中止。采用 UBSan 构建时，启用的检查还可以通过 trap 暴露相应的未定义行为。程序自己的 assert、abort 及导致中止的未捕获异常，也能形成被目标排除的失败路径。模型不支持的指令或系统调用则属于覆盖范围问题，同样会妨碍相应无错误命题成立。公开命题中的错误分类

因此，把这条路线概括成“检查硬件异常，并通过 sanitizer 把其他错误编码成硬件异常”，抓住了把性质转成失败分支的思路，但信号范围还要扩大：它排除的是语义与命题规定的错误或中止；硬件故障、显式 trap、运行时 abort 和模型未覆盖，并非同一种机制。 系统调用返回错误码也不自动等于 crash，程序可以正常处理失败；是否允许这种执行，要看命题与环境前提。

如果 RTE 指 C 源码验证中的运行时错误，它通常还包含非法指针访问、算术溢出等未定义行为。Frama-C 的 RTE 插件就为这类表达式生成需要证明的断言。机器级无 crash 并不会自动恢复全部源语言要求。Frama-C 对 RTE 的定义

一个解释性例子是整数除零：

int divide(int x, int y) {
    return x / y;
}

在 C 中，y == 0 是需要排除的运行时错误；但若生成的机器代码直接执行 RISC-V 整数除法指令，除零不会触发硬件异常，而会返回指令集规定的结果。LPS 的 mul_div 也明确实现了这一规则。没有额外检查时，“这段二进制不崩溃”不能推出“源程序没有发生除零”。RISC-V 除法规范、LPS 除法定义

启用相应 UBSan 检查并采用 trap 等失败策略，可以把这种情况转成证明必须排除的分支。有符号溢出、非法移位等也要逐项核对检查配置；启用 ASan 不等于启用 UBSan，存在 UBSan 构建也不等于所有入口启用了全部检查。UBSan 检查与失败策略

这说明有两种彼此独立的边界：语义是否忠于真实机器，以及命题是否覆盖所关心的源语言错误。即使机器语义完全正确，未被定义为错误、也没有被插桩暴露的源码级 RTE，仍可能不受这个无 crash 目标约束。扩大信任证据与扩大性质覆盖，需要分别推进。

6.7 排序怎样变成可执行规约：检查器承载了什么义务

原文把主要工作方式概括为让 “this test suite always passes” 成为形式命题。沿着这种无错误模板，功能要求也可以先写成程序中的检查，失败时调用 abort 或触发断言，再证明失败路径不可达。这是将性质编码为可执行失败条件，并不局限于硬件自动产生的异常。原文对规约的说明

以整数排序为例，如果继续使用“入口不失败”这个模板，可以先保留原始输入，再运行排序，并检查输出有序且元素多重集合保持不变。下面是解释性伪代码，既不是论文发布的排序实验，也不是已经验证的检查器：

before = copy(input)
after = sort(input)
if not (ordered(after) and
        same_multiset(before, after)):
    abort()

这里的 same_multiset 必须比较重复次数，不能只检查出现过哪些元素。仅检查有序、长度相同、总和相同，甚至再加异或值相同，也仍然不充分。例如 [1, 2, 3] 与 [0, 3, 3] 都有序、长度均为 3、总和均为 6、异或值均为 0，但后者显然不是前者的排列。

如果要从“检查程序不失败”推出排序性质，需要建立检查器的成功意味着真实性质成立。将正确排序性质缩写为 FFF，至少要有下面这种可靠性关系，并保证检查器会终止返回：

Check⁡(before,after)=true⟹F(before,after). \begin{aligned} &\operatorname{Check}(before,after)=\mathrm{true}\\ &\qquad\Longrightarrow F(before,after). \end{aligned} ​Check(before,after)=true⟹F(before,after).​

具体义务还包括：输入副本确实在排序前保存且未被破坏，比较顺序与预期一致，检查覆盖全部相关元素和路径，失败确实触发被命题禁止的结果，检查器自身没有溢出、越界或挂起。若检查器在错误输出上无限循环，单纯的无 crash 性质仍可能成立；若输入与输出实际上别名到同一份已修改数组，排列检查也可能退化成对象与自身比较。

把功能要求写成可执行检查，并不会消除规约正确性的义务。 它把一部分义务落实为检查器及其与数学性质的对应。这个对应可以证明，也可以先用测试与独立审查增加信心；两种证据应明确区分。仅证明一个遗漏要求的检查器不会报错，得到的仍然只是那个较弱的目标。

同时，“排序只能插桩，不能用 Rocq 的 Permutation 和 Sorted”也不是框架的固有限制。可以直接提出下面这样的逻辑目标；这里 before、after 表示整数列表，片段仅示意性质：

Permutation before after /\
Sorted Z.le after

Permutation 描述排列关系，Sorted 描述给定关系下的有序性。Rocq 的排列定义、有序性定义 要将它们用于二进制程序，还需定义机器内存怎样表示这些列表，并证明程序执行前后的表示关系。这样做是在使用同一类形式语义提出更强的功能命题，已经超出直接复用现有无错误模板的那一步。

另一种做法是证明可执行检查器与这些 Rocq 性质相对应，再把检查器接回入口。由此可以将通用无错误模板与已有的高层数学定义结合起来，而不必让检查器的正确性永远留在未经论证的信任中。若只证明“排序返回时结果正确”，还应与“排序一定返回”的终止性质分开。

这条路线很有吸引力的一点，是能够复用维护者已经写好的可执行检查，让模型集中处理庞大的执行证明。对完整功能正确性，难点则会进一步落到检查器是否充分、编码是否保持要求、数学性质是否忠于需求。困难的工作可以交给模型，但这些正确性义务仍然需要有明确的承担位置。

对于排序，直接证明 Permutation 与 Sorted，或者先证明检查器与它们对应，都是值得采用的路线。选择可执行规约能够改变工程组织方式；它不会自动解决规约是否正确，也不必放弃已有形式定义与引理的复用。

6.8 排除证据更强，不等于找漏洞的效率必然更高

完成的全称证明提供更强排除证据，但不意味着找漏洞在所有任务与相同预算下都更高效。发现能力应统一入口、输入、构建与资源，比较确认缺陷、遗漏和总成本；保证能力则应核对完成命题及信任前提。

7. 还有哪些研究方向：把成果变成可信、可复用的保证

7.1 规格生成需要独立的正确性与充分性评价

规约可以是逻辑公式，也可以是可执行检查、参考算法或抽象状态机。 关键在于观察什么、允许哪些输入和行为，以及要求是否独立约束实现。解析器的接受与输出、权限检查的拒绝条件、数值程序的误差及特殊值，都需要具体定义。

code2spec 若只按原实现能否证明评分，会奖励恒真条件、遗漏失败情况的前提或对实现的机械复述。独立需求、参考模型、审查和变异程序可以检验漏项：排序只要求有序会允许丢元素，还需保留多重集合；拒绝若干变异体也不等于证明规约完整。

对操作系统，可以由人给出抽象状态转换，让模型寻找实现与抽象状态的关系及不变量。这样可能减少精化证明的人工负担，但允许行为、环境假设和状态对应的义务仍然存在。

7.2 让模型 formalize，再测试 formalization，能走多远

值得尝试的路线是：让模型把代码 formalize 到 Rocq 或 Lean，测试形式化，再证明功能性质。 需要对照输入输出、中间状态和错误行为，记录支持子集及失败案例；若形式化正确仍是工程假设，就不能把它当作已完成的原程序保证。

源码、IR 与二进制各有适用场景，重点是保留哪些执行、增加哪些前提，以及结论如何传递。浮点 C 尤其不能由实数公式代替：舍入、NaN、无穷大、有符号零及编译选项都可能改变行为。只保留正常返回的模型，也可能完全遗漏原程序错误；有界检查、差分测试与证明应分别说明范围。

证明有机会替代固定性质与产物上的重复测试，但真实重放、模型对照与部署变化仍需检验。

7.3 模块化抽象需要证明它能改善后续任务

分配器契约、调用约定和分离逻辑规则，应让后续程序在明确前提下复用。评价时应测量跨程序、跨版本的预算节省、维护成本及模型升级后收益，不能只看当前证明缩短多少。

7.4 评测要同时约束目标、实现和资源

规约用独立需求、漏项反例与变异检验评价；模型用执行对照、对应定理与错误路径保留评价；复用用固定依赖的新任务和跨版本实验评价；补丁用合法输入、变化范围和回归证据评价；成本用强代理基线、完整成功率和总账单评价。

需要防止同一生成过程同时决定需求、实现、规约与验收，最后只报告全部通过。关键目标和检查方式应有独立约束，并记录每次有意义的改变。

7.5 更强的模型，要求更准确的保证表述

这项工作令人兴奋，也给小型团队带来压力：大量局部执行推理正在成为通用代理能力。人类把握宏观设计、模型持续推进繁重证明的组织方式，已经值得认真采用。

后续价值在于把需求、形式语义、补丁与部署接成可复现的证据链，并交付可复用的接口与完整成本。可信程度取决于陈述、前提、产物和检查过程，不能只看证明规模。
