形式化验证

Anthropic 的程序验证：测试 formalization 而不是实现，功能性检查编码到 crash，不写 spec 只写证明

从二进制操作语义与 fuzz 规约出发，讨论找 bug、功能正确性与大模型时代的信任取舍。

黑色为原文、附录与公开源码中的内容；橙色为补充讨论、例子与评价。

0. 背景知识：Fuzz、sanitizer、ASan 与 LPS

0.1 Fuzz：自动生成输入，寻找失败执行

Fuzz testing（模糊测试） 反复生成半随机输入或变异已有输入，再把它们交给开发者编写的 fuzz target（测试入口）。入口调用库 API，并可用断言检查结果；导致 crash 的输入被保留下来。原文从 OSS-Fuzz 已有的入口出发，把“继续寻找失败输入”改成“证明指定范围内的所有输入都通过检查”。原文对 fuzzing 的说明

以图片解析器为例：不断改动文件头、尺寸和压缩数据，再调用解析函数，就是 fuzzing。libFuzzer 还会记录触及了哪些代码，把到达新路径的输入留下来继续变异；这叫覆盖率引导。libFuzzer 官方说明

0.2 Sanitizer：给执行中的程序增加检查

Sanitizer 是本文所用运行时检查工具的统称。编译器把检查插入程序；运行时一旦发现对应违规，就报告错误并按配置中止或触发 trap。ASan（AddressSanitizer） 用于发现缓冲区越界、释放后使用等内存错误。原文把它加入 fuzz 程序，使这些内存错误能够表现为测试失败。原文脚注 4

公开证明仓库还分别提供 ASan、UBSan 和二者组合构建的目标。证明对象包含这些实际编译进去的检查。cJSON 的构建与目标

0.3 ASan 的直观例子：在对象边界布置警报

可以把进程的可访问地址空间想成仓库，把一次分配得到的缓冲区想成箱子。操作系统的页级保护通常不会为每个小对象单独立墙：写出了箱子，却还在可写的仓库区域里，程序可能暂时正常运行，只是已经破坏了数据。

ASan 通过编译时插桩与运行时库，为许多内存访问增加检查，并用影子内存记录地址是否允许访问。可以把它理解为在部分边界和失效区域布置警报。某次访问命中禁用区域，便报告错误并通常中止程序。ASan 的组成与工作方式

例如，假设驱动分配了 16 字节的堆缓冲区 p，输入控制索引 i，随后调用这个解释性示例：

void put(char *p, size_t i) {
    p[i] = 1;
}

i == 16 时，尝试写入的是第 17 个字节。普通构建可能破坏邻近数据而没有立即崩溃；在 ASan 构建中，如果目标地址被标记为禁用区域，相应检查会报告越界并中止。于是，一个原本可能静默的内存错误，被转换成 fuzz 驱动与无错误命题能够观察到的失败。

输入控制索引
  → 执行一次写入
  → ASan 检查目标地址
  → 命中禁用区域，报告并中止

对某个输入运行一次，能够发现这次执行中的报告；形式证明进一步尝试排除前提范围内所有执行的这种失败。两者使用同一类可执行检查，但覆盖的量词不同。检查配置和二进制共同固定证明对象。

0.4 LPS：在 Rocq 中定义二进制怎样运行

LPS（Linux process semantics） 是 Theorem 用 Rocq 写出的 Linux 进程形式模型。它描述 64 位 RISC-V（RV64GC）二进制的指令执行、内存、系统调用和可观察事件，并提供行为一致、无错误和终止等命题及证明库。LPS 仓库说明

在主实验中，二进制 给出要执行的指令，LPS 规定指令和进程怎样执行，spec 规定要排除什么错误及比较什么行为，Claude 生成证明，Rocq 内核 检查证明项是否具有指定命题的类型。原文图 2 与公开检查流程

可以把 LPS 想成写在证明器里的机器说明书：一条加载指令怎样取内存，写入失败怎样分类，read 可以返回哪些结果，都由它定义。形式证明沿这份说明书推理，因而模型是否准确成为保证能否落到真实机器上的关键。

2.4 要证明的命题，比“不会崩溃”更具体

主实验的输入上限为 64 MiB 以下，环境限定为受支持的单线程、静态 RISC-V/Linux 进程，并带有具体资源和环境前提。这些限制属于命题本身；更大的输入、不同架构或不同运行方式，需要相应的模型与证明。主实验范围

公开仓库区分 终止性质（halts） 与 行为一致性质（agreement）。前者在资源与环境前提下要求正常退出；后者比较普通构建和 sanitizer 构建的有限行为轨迹集合，并分别要求两者无错误。plain_halts 的 16 GiB 是资源前提，终止是需要单独完成的目标。定理陈述文档

入口安全 描述指定入口、输入、构建与执行语义中的失败路径；构建一致性 描述两组可观察行为之间的关系。

断言性质 由入口实际检查的条件给出；完整功能要求 则需要表达预期的接受条件、输出与状态变化。

输入范围、错误定义和功能要求共同确定要证明的命题。

一个始终返回错误码的解析器可能很安全。要保证它有用，还要约束合法输入的接受和解析结果。功能要求可以通过断言进入证明，也可以直接写成高层规约。

2.5 证明规模：运行时占据了什么工作

附录报告，尝试过程中产生约十亿行 Rocq，其中约 1.8 亿行属于成功证明。大量内容由工具和脚本生成，单个证明的检查也需要明显的计算时间。附录第 3–4 页

附录用 cJSON 说明规模反差：391 行解析入口对应约 63 万行证明，只有约十分之一围绕 cJSON 本身；链接约 5.1 万行代码的 fftw3 对应约 48 万行证明。典型交付约 60 万行、1,400 个文件，不同库的证明约为 33 万至 90 万行。启动过程、分配器、输出函数、ASan 运行时和驱动都要处理，当时这些共同结果尚需在各证明中处理。超过一半的文本由代理编写的工具生成；约 40% 属于定义、模型、引理与证明步骤等证明正文，其中一部分仍由脚本生成。典型入口的几百行 C 代码可能只编译为约 2,000 条指令，但完整进程的证明仍要处理上述公共组件。检查一个证明可消耗半小时到数小时 CPU 时间。附录第 3–4 页

启动、运行时与分配器构成大量共同工作。把这些工作封装成可直接引用的模块，可以同时节省生成、维护与检查成本。

附录补充：专家观察到的短规约与抽象

附录中的专家观察是，代理经常先写一个描述输出的短规约，再把两个构建分别与它联系起来；这类规约的中位数约 110 行，对应程序机器代码中位数约 86 KB，其中驱动实际涉及约 20%–50%。证明过程却反复展开寄存器、整数转换、地址互异、栈内容与各分支。代理也使用了 framing、布局无关推理和分配器抽象，但使用并不一致，证明规模改善仍有限。附录将更复杂程序上的规模扩展列为开放问题，并以 MachCSL 等其他代理验证项目遇到的复杂度问题，讨论建立更好模块抽象的必要性。后续问题包括：合适抽象是否需要专家证明工程师指导，还是可以提炼通用原则，让代理自行发现支持扩展的抽象。附录第 4–5 页

中间规约的区分能力决定了它能支撑什么关系。例如，输出 0 与输出 1 都满足“输出非负”；要证明两个程序行为一致，就需要刻画各自全部可观察轨迹。下文 cJSON 的 *_obs_iff 正是这种双向刻画。

抽象的价值集中在扩展、复用、调试和成本。让模型自行找到有效的模块边界，是比模仿人类证明风格更直接的研究目标。

2.6.3 完整目标：量词、预算、三个结论与单独的终止义务

Shapes.v 的 agrees_in 完整定义如下，保留全部量词、前提与三个结论：

Definition agrees_in (env : SpuriousCfg) (lim_plain lim_san : Z) (plain san :
  Image) : Prop :=
  forall (en_plain en_san : ExecEntry) (inp : ProcInput),
    valid_entry plain en_plain inp ->
    valid_entry san en_san inp ->
    valid_input inp ->
    ~ run_scfg_budget_refused env plain lim_plain en_plain inp ->
    error_free (run_scfg env plain lim_plain en_plain inp)
    /\ error_free (run_scfg env san lim_san en_san inp)
    /\ trace_equiv (bh_traces (run_scfg env plain lim_plain en_plain inp))
                   (bh_traces (run_scfg env san lim_san en_san inp)).

外层对两个构建的启动布局和进程输入分别全称量化。进程输入包括参数、环境变量、初始文件、标准输入等；启动布局包括栈、堆起点和相关随机字节。两个构建的布局不必相同。前提成立后，要得到普通构建无错误、插桩构建无错误，以及两者有限轨迹集合相同。

逐行读这段 Rocq：forall 量化固定映像下所有合法进程输入与两个独立的启动布局；连续的 -> 引入必须满足的前提；~ run_scfg_budget_refused ... 是对普通构建运行的预算前提；最后的 /\ 把三个义务合取。第一项直接要求普通构建无错误。第三项比较两组可能的有限轨迹。

run_scfg 的参数依次给出环境失败策略、二进制映像、预算、启动布局和输入。cJSON 的 ASan 一致性目标采用普通构建 2 GiB、插桩构建 512 GiB 的预算；普通终止目标另用 16 GiB。alloc_forced_only 要求内存请求只在预算耗尽或找不到可用地址范围时失败，其他种类的请求仍可能失败。参数与模板定义

真实 spec 的难点集中在量词和前提：环境失败怎样允许、预算放在哪个构建上、轨迹怎样比较。这些选择直接决定证明难度与保证范围。

再对照同文件中的终止模板。终止模板使用谓词 must_exit_in_scfg：

Definition halts_within_budget (lim : Z) (allowed : list word) (img : Image) :

    ~ run_scfg_budget_refused forced_only_cfg img lim en inp ->
    must_exit_in_scfg forced_only_cfg allowed img lim en inp.

它要求每一条允许执行最终正常退出，且状态属于 allowed；因而同时排除无限执行、卡住、错误和信号终止。forced_only_cfg 还禁止环境无缘无故拒绝请求，比一致性目标的 alloc_forced_only 更强。代入 cJSON 的 plain_halts 后，预算是 16 GiB，允许退出状态为 0 或 2；这个目标在固定 README 中为 open。

ASan 没有任意环境失败下的同类 halts_may_fail 目标：运行时的启动地址空间预留若被拒绝，会刻意等待不结束。

进程层的 sstep 是一步转换关系。以下是 Run.v 的实际故障构造子，从归纳定义中原样节选：

| sstep_instr_fault : forall ms model,
    m_halted model = None ->
    ms_svc_pending ms = None ->
    mi_account_step ms model = MachineFault ->
    sstep (mkCfg ms model) [] SError

三个箭头前提分别要求进程尚未正常退出、当前没有待处理系统调用，以及本次机器步进确实产生 MachineFault；满足后，结论就是存在一步到达 SError。相邻的 sstep_instr_unmodeled 规则把 MachineUnmodeled 也送到 SError。系统调用另有规则；返回错误码也是程序可以处理的正常结果。

接着，star 连接零步或多步正常转换，reaches_error 的定义把“某条执行能出错”精确写成存在量词：

Definition reaches_error (c0 : config) : Prop :=
  exists tr c evs, star c0 tr c /\ sstep c evs SError.

exists tr c evs 提供反例执行的见证：从初态 c0 沿轨迹 tr 到达 c，再由一步 sstep 进入错误。只要存在一个这样的见证，无错误命题就不成立；证明无错误要排除全部见证。

Definition MAX_INPUT : Z := 67108864%Z.

Definition t_body (data : list byte) (fs : Fs.Fs) : TSet :=
  let len := length data in
  if (MAX_INPUT <=? Z.of_nat len)%Z then t_die msg_refused fs
  else if (len <? 6)%nat then t_die msg_short fs
  else
    let b0 := bv_unsigned (nth 0 data (Z_to_bv 8 0)) in
    let b1 := bv_unsigned (nth 1 data (Z_to_bv 8 0)) in
    let b2 := bv_unsigned (nth 2 data (Z_to_bv 8 0)) in
    let cfg := (b0 + 256 * b1)%Z in
    let config_len := Z.to_nat (cfg mod 32768) in
    if (len <? 6 + config_len)%nat then t_die msg_overrun fs
    else
      let calls := match config_len with O => 1%nat | _ => S (Z.to_nat (b2 mod 4))
        end in

  - cbn. eapply AS.SpinAlg.srealizes_no_error; exact Htarget.

3.4 补充讨论：怎样把排序要求编码为检查

原文把主要工作方式概括为让 “this test suite always passes” 成为形式命题。沿着这种无错误模板，功能要求也可以先写成程序中的检查，失败时调用 abort 或触发断言，再证明失败路径不可达。功能要求由此编码为可执行失败条件。原文对规约的说明

以整数排序为例，如果继续使用“入口不失败”这个模板，可以先保留原始输入，再运行排序，并检查输出有序且元素多重集合保持不变。下面用排序作补充示例：

before = copy(input)
after = sort(input)
if not (ordered(after) and
        same_multiset(before, after)):
    abort()

same_multiset 比较元素及其重复次数。只比较出现的元素、长度、总和或异或值，都会遗漏要求。例如 [1, 2, 3] 与 [0, 3, 3] 都有序，长度均为 3、总和均为 6、异或值均为 0；二者的多重集合不同。

如果要从“检查程序不失败”推出排序性质，需要建立检查器的成功意味着真实性质成立。将正确排序性质缩写为 FFF，至少要有下面这种可靠性关系，并保证检查器会终止返回：

Check⁡(before,after)=true⟹F(before,after). \begin{aligned} &\operatorname{Check}(before,after)=\mathrm{true}\\ &\qquad\Longrightarrow F(before,after). \end{aligned} ​Check(before,after)=true⟹F(before,after).​

具体义务还包括：输入副本确实在排序前保存且未被破坏，比较顺序与预期一致，检查覆盖全部相关元素和路径，失败确实触发被命题禁止的结果，检查器自身没有溢出、越界或挂起。若检查器在错误输出上无限循环，单纯的无 crash 性质仍可能成立；若输入与输出实际上别名到同一份已修改数组，排列检查也可能退化成对象与自身比较。

可执行规约把一部分功能义务交给检查器：成功意味着目标性质成立。这个对应关系可以通过证明建立，也可以先用测试和独立审查检验。

5.2 找 crash、无 crash 与完整内存安全

找到并确认一个 crash：给出具体输入和环境，在真实目标重放失败，并确认违反预期契约。

指定插桩构建无 crash：排除前提范围内全部执行中的规定错误，包含相应检查失败，并建立形式模型与真实执行的对应。

5.3 补充例子：ASan 的检测范围与漏检

ASan 的内存访问检查可能遗漏几类情况。对象内部越界，例如数组成员越界覆盖同一结构体的后续成员，默认检查未必区分内部边界。错误访问落入另一个活对象 时，目标地址仍可访问，ASan 未必知道指针本应属于另一个对象。未插桩代码中的普通访问 则可能没有相应检查；拦截器可以覆盖部分操作，但不能视为全面覆盖。

逻辑有效长度 也是另一种边界：分配 1,024 字节、只有前 64 字节有效时，读取第 100 字节可能不报错，需要长度不变量或相应标注。未初始化值的使用 主要由 MemorySanitizer 检查；整数溢出、非法移位等未定义行为 需要相应 UBSan 配置；数据竞争 由 ThreadSanitizer 等检查，而主实验限定单线程。

功能或权限错误，例如输出内容错误、遗漏权限检查，通常还需要功能规约或断言提供判断标准。通用 sanitizer 不会自动知道业务预期。

公开 cJSON 命题明确列出“访问落入另一个活对象”和“未插桩代码”两类限制。项目中的明确说明 容器内部逻辑边界可以通过专门标注增强检查；逻辑有效数据边界依赖相应标注。ASan 容器检查说明

一个更容易看见的对象内部越界例子如下，同样是解释性示例：

struct S {
    char data[8];
    int allowed;
};

void put_member(struct S *s, int i) {
    s->data[i] = 1;
}

在常见布局下，i == 8 可能写到 allowed 的字节。它已经越过 data 的数组边界，却仍处于整个结构体对象内部；默认 ASan 可能不报警。用箱子比喻，这相当于破坏了箱子内部的隔间，但没有碰到外侧警报。某些 UBSan 边界检查或额外布局插桩可以覆盖部分此类情况。ASan 开发者对内部越界的说明

其他 sanitizer 也各有目标：MemorySanitizer 关注未初始化值的使用，UBSan 覆盖启用的未定义行为检查，ThreadSanitizer 检测数据竞争。实际检查集合由构建配置决定，业务要求由功能规约或断言给出。

形式证明把“警报在样本中没有响”推进为“允许执行中警报都不响”。要扩大保证范围，可以继续补充对象归属、子对象边界和业务要求，并把它们纳入模型与命题。

一个解释性例子是整数除零：

int divide(int x, int y) {
    return x / y;
}

在 C 中，y == 0 是需要排除的运行时错误；但若生成的机器代码直接执行 RISC-V 整数除法指令，除零不会触发硬件异常，而会返回指令集规定的结果。LPS 的 mul_div 也明确实现了这一规则。这条机器指令的正常结果，和 C 源语言要排除的除零是两个层次。RISC-V 除法规范、LPS 除法定义

启用相应 UBSan 检查并采用 trap 等失败策略，可以把这种情况转成证明必须排除的分支。有符号溢出、非法移位等也要逐项核对检查配置；实际启用项由各入口的构建配置决定。UBSan 检查与失败策略

5.5 形式化错误影响什么结论

继续使用仓库的比喻：形式语义像一份描述通道、边界和警报器的地图。依据地图找到可疑位置，再到真实仓库确认确实出错，这个发现不因地图其他地方画错而失效。反过来，仅在地图上证明所有路线都安全，结论能否适用于仓库，就取决于地图是否保留了真实可能发生的危险。

找 bug：
  模型提供候选输入
  → 真实目标复现失败

提供保证：
  模型内完成全称证明
  ＋ 模型与真实执行的可靠对应
  → 前提范围内排除规定错误

形式化错误会带来漏报或无法复现的候选输入。真实目标上已复现并确认的 bug 仍然有效。对全称保证，模型需要覆盖真实执行并保留错误：把本应失败的操作写成正常后继，会让错误模型中的无错误证明与真实程序脱节。

对全称安全性质，保守覆盖真实执行可以足够；行为等价还要处理模型额外允许的行为。差分执行、独立审计和参考语义的对应证明，可以逐步加强这条联系。

语义错误影响从模型结论到真实程序的推导；检查链错误则影响模型内证明的有效性。项目的信任基础

找漏洞可以先采用经过测试、仍有缺口的地图，再到真实程序确认发现。提供全称保证，则要建立地图与真实执行之间的可靠对应。

6. 结论（Conclusion）

原文展望，形式验证将逐步成为生产软件开发内置的环节，像类型系统与测试框架一样进入日常工作流。模型能力、语言设计和开发流程共同推动这一变化。原文结论

6.1 规格生成需要独立的正确性与充分性评价

规约可以是逻辑公式、可执行检查、参考算法或抽象状态机。 解析器的接受与输出、权限检查的拒绝条件、数值程序的误差和特殊值，都可以据此提出。

code2spec 可以用独立需求、参考模型、审查和变异程序评价。排序要求有序并保留多重集合；操作系统可以先给出抽象状态转换，再让模型寻找实现与抽象状态之间的关系和不变量。

6.2 让模型 formalize，再测试 formalization，能走多远

让模型把代码 formalize 到 Rocq 或 Lean，测试 formalization，再证明功能性质，是一条值得投入的路线。模型测试应对照输入输出、中间状态、错误和发散，记录支持子集与失败案例；对应证明进一步连接形式模型与原程序。

源码、IR 与二进制可以服务于不同任务。浮点 C 的模型需要表达舍入、NaN、无穷大、有符号零和编译选项。固定性质和产物上的证明，可以减少重复测试，把测试资源更多投入语义、环境和版本变化。

6.3 模块化抽象需要证明它能改善后续任务

分配器契约、调用约定与分离逻辑规则，应以跨程序和跨版本的预算节省、维护成本、模型升级后的收益来评价。

6.4 评测要同时约束目标、实现和资源

规约评价需求覆盖，模型评价执行对应，复用评价新任务收益，补丁评价行为变化，成本评价完整交付。关键需求和验收方式由独立证据约束，并记录每次有意义的改变。

6.5 更强的模型，要求更准确的保证表述

大量局部执行推理正在成为通用代理能力。人类把握宏观设计、模型持续推进繁重证明的组织方式，已经值得采用。

后续研究可以把重点放在需求、形式语义、补丁与部署之间的对应，交付可复用接口与可复现的完整成本。
