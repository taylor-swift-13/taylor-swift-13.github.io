## 1. 引言：程序验证开始成为一种规模化生产

2026 年 10 月 22 日，Anthropic 与 Theorem 发布了 [*LLMs are making formal software verification feasible at a much larger scale*](https://www.anthropic.com/research/formal-verification)。作者报告：在数周内，为 **123 个开源库的 239 个 fuzz 入口**完成了特定条件下的 RISC-V 二进制证明，成功证明包含约 **1.8 亿行 Rocq**。这组数字对应实验报告的结果，公开发布的证明只是其中一部分。

## 2. 从 fuzz 测试到二进制证明

### 2.1 图 1：测试找到反例，证明覆盖一个明确的输入范围

OSS-Fuzz 中的 fuzz target 是开发者提供的测试入口。它接收输入、调用库代码，并可能用断言检查结果。Fuzzer 不断寻找会让入口崩溃的输入；OSS Verify 则尝试证明，在陈述规定的范围内不存在这样的输入。[Theorem 项目说明](https://theorem.dev/oss-verify/)

@@anthropic-figure-1@@

*原文图 1：fuzzing 的搜索过程。动画中，一次执行只走过迷宫中的一条路径；红色表示触发崩溃，绿色表示相关问题被修补。不断增加测试次数，会扩展已经尝试过的部分，但迷宫中仍有尚未走到的区域。图为原文示意动画，并非实验覆盖率数据。[原始动画](https://cdn.sanity.io/files/4zrzovbb/website/6851e539c36759ac1682d6b169d0319b1d97a0f7.mp4)*

@@opinion-begin@@

图 1 先交代了这条路线为什么值得尝试：测试能很快确认一个具体反例，却可能很久也碰不到触发它的输入。对越界访问、计数器溢出或特殊调用历史，寻找输入和确认错误的难度可能相差很大。让模型在证明中分析所有相关分支，有机会覆盖普通 fuzzing 很难到达的路径。

这里发生了一个量词上的变化。一次成功测试说明某个输入没有触发失败；一个正确的全称命题，要求范围内的每个输入都满足条件。不过，图中的“所有”仍然需要输入范围、入口、环境和失败定义作限定。

@@opinion-end@@

### 2.2 图 2：程序、语义、规约和证明如何连接

项目把库和 fuzz driver 编译成静态 RISC-V 二进制，在 Rocq 中用 **LPS（Linux process semantics）**解释机器指令、进程启动和系统调用，再为指定二进制提出命题。公开仓库的声明直接引用二进制映像；编译器正确性及源码与二进制的对应关系不属于这些声明。[公开证明仓库](https://github.com/theorem-labs/oss-verify-proofs)、[信任基础说明](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/docs/trust.md)

@@anthropic-figure-2@@

*原文图 2：从源代码到机器检查过的结论。沿横向依次是源代码、RISC-V 可执行文件、形式陈述、证明。蓝色框标出所依赖的性质定义、机器与操作系统语义、证明检查器；动画中的红色表示证明被拒绝，绿色表示检查通过。绿色结论仍以蓝色部分正确为条件。[原始动画](https://cdn.sanity.io/files/4zrzovbb/website/ce66333a831ef2f37e91c2f0ecfdaca27cdfa2c9.mp4)*

图 2 中最容易被忽略的是蓝色的语义框。LPS 提供了连接机器代码与 Rocq 命题的执行定义：指令解码器识别二进制指令，执行语义规定寄存器、内存和程序计数器怎样变化，进程模型连接系统调用、输入输出与错误。公开源码中的 [`Decode.v`](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/Riscv/Decode.v) 和 [`Run.v`](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/LinuxProcessSem/Run.v) 分别展示了解码和执行关系。

用一个简化的式子概括“不出现规定的错误”这个目标：

$$
\forall x\in D,\ \forall e\in E,\ \forall s_0\in\operatorname{Init}(B,x,e),\ \forall s,\quad
\operatorname{Reach}_{\mathrm{LPS}}(s_0,s)\Longrightarrow\neg\operatorname{Bad}(s).
$$

这里 $B$ 是指定二进制，$D$ 是允许的输入集合，$E$ 汇总允许的环境与内存布局，$\operatorname{Reach}$ 是 LPS 定义的可达关系，$\operatorname{Bad}$ 表示相应命题排除的错误。这个式子是本文示意，实际定理还区分终止、行为一致和资源前提；**没有运行错误，不等于已经证明终止**。

因此，它需要定义目标指令集的语法和执行规则，以及相应的系统环境；它不需要为每一种源语言重新实现整套前端语法。不同源语言编译到受支持的机器代码后，可以共享这层语义，但运行时、并发、动态加载等行为仍须落在模型的支持范围内。[LPS 结构说明](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/README.md)

@@opinion-begin@@

这条路线的吸引力，在于把程序特有的建模工作集中到一个可复用的执行语义中。面对另一个库，可以继续使用同一套指令和系统调用模型。代价是必须处理寄存器、内存布局、运行时和库函数等低层细节，证明规模很容易膨胀。

如果拿 QCP 这类源码验证框架作参照，这里同样有一层“程序怎样执行”的正式定义。区别在于，前者可以围绕 C 程序组织符号执行和验证条件，后者把关注点放在机器代码与 Linux 进程模型上。Rocq 不会凭空理解可执行文件；困难只是被放到了另一层，并由模型在这一层上建立证明。

二进制验证也改变了结果的身份。被证明的是一份具体的可执行文件；更换编译配置、链接依赖或目标架构以后，需要重新建立结论。一个证明可以非常可靠，同时只对很具体的一份软件产物有效。

@@opinion-end@@

### 2.3 图 3：把可执行检查变成规约，并在证明途中找 bug

从 fuzz 程序得到规约，并不要求先从零写出整个库的功能定义。入口、被调用的实现、sanitizer 和已有断言共同构成可执行的检查；项目再要求，在给定输入和环境范围内，这个检查程序不会到达规定的错误。已有断言检查了什么，生成的证明目标就可能间接约束什么。[定理陈述说明](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/docs/statements.md)

@@anthropic-figure-3@@

*原文图 3：证明从一个入口出发逐步覆盖可达路径。绿色区域随证明推进而扩展，红点表示证明过程中遇到的问题。动画最后仍有灰色区域，因为这些代码无法从当前入口到达。它展示了入口证明和整个程序覆盖之间的区别。[原始动画](https://cdn.sanity.io/files/4zrzovbb/website/53266e21746d781c80dbe9296b90da94b676dd67.mp4)*

@@opinion-begin@@

“无法证完”需要诊断：可能是性质不成立，也可能是辅助引理缺失、抽象不合适、语义尚未覆盖，或者预算用尽。一次失败的证明尝试本身不构成漏洞证据；可复现的反例或形式化的否定结论才把问题坐实。

针对找 bug 的目标，可以接受仍有缺口但能够提供有效线索的形式化。一个有缺口的模型仍可能帮助发现真正的崩溃输入；把输入放回真实程序与相应环境中重放，确认错误后，它就成为有用的工程成果。模型中出现的错误可能只是建模问题，候选输入也必须经过这一步确认。

这和“程序已经没有这类 bug”需要的证据不同。**找出一个可复现的错误，可以不以整套语义完美为前提；排除范围内的全部错误，则高度依赖语义与规约的可靠性。** 这篇工作值得重视的一点，就是即使整项证明尚未完成，寻找证明的过程仍可能交付真实反例。比较工具时，应把复现漏洞的数量、误报和成本也算进去。

相应地，图中的绿色有清楚的起点。它表示当前入口及其前提允许的执行已经得到证明。另一个调用者、另一套调用顺序，可能进入这张图中尚未涉及的部分。

@@opinion-end@@

### 2.4 要证明的命题，比“不会崩溃”更具体

主实验的输入上限为 **64 MiB 以下**，环境限定为受支持的单线程、静态 RISC-V/Linux 进程，并带有具体资源和环境前提。这些限制属于命题本身；更大的输入、不同架构或不同运行方式，需要相应的模型与证明。[主实验范围](https://www.anthropic.com/research/formal-verification)

公开仓库区分了 **终止性质（halts）**和 **行为一致性质（agreement）**。前者在相应资源与环境前提下要求执行正常结束；后者比较普通构建和 sanitizer 构建的有限行为轨迹集合，并排除规定的错误。行为一致本身不排除挂起。默认 `plain_halts` 的内存前提，也不能读成“程序最多使用 16 GiB 内存”的结论。[定理陈述文档](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/docs/statements.md)

**表 1：几种容易混淆的结论（本文整理）。**

| 结论 | 需要读清的范围 | 能否直接推出整个库功能正确 |
| --- | --- | --- |
| 测试入口不触发规定的错误 | 指定入口、输入范围、构建和执行语义 | 不能 |
| 普通构建与插桩构建行为一致 | 所选可观察事件，以及两组行为的比较方式 | 不能 |
| 入口中的断言总是成立 | 断言写了什么，什么前提下执行到它 | 只覆盖所写性质 |
| 程序满足完整功能规约 | 规约覆盖哪些需求，是否忠于原始意图 | 仍需检查规约与现实的对应 |

表 1 将入口安全、两个构建的一致性、断言性质和完整功能要求分开。读表时要连同第二列的范围一起看：增加输入范围、改变错误定义或加强功能要求，都会改变实际需要证明的命题。

@@opinion-begin@@

主实验的主要局限在于：它以可执行安全检查为中心，距离一般软件的完整功能正确性还有很长一段路。这种规约的外层陈述比较简单，真正困难的执行分析可以交给模型不断推进；但通过这个目标，不能直接回答解析结果是否正确、权限是否按设计实施、系统状态是否满足用户要求。

不过，“主要验证安全性”需要保留“主要”两个字。入口中的断言可以表达功能要求；某些安全证明内部也可能必须建立复杂的功能不变量。局部功能性质和完整功能规约之间，仍然有很大差别。

例如，一个始终返回错误码的解析器可能很安全，却没有完成解析任务。要排除这种实现，规约就必须要求它接受某些合法输入，并返回相应结果。安全、功能、终止和可用性，需要分别写清再连接起来。

@@opinion-end@@

### 2.5 断言能够表达功能要求，其他实验也有不同的保证

原文还报告了针对 x86 二进制的 zlib 格式规约验证，以及使用 Verus 验证一个以 Rust 编写的 Python 子集解释器。它明确说明，**x86 实验采用 Claude 生成并经过大量测试的 ISA 语义**；RISC-V 主实验使用的是 Theorem 的 LPS。原文的这一说法不能直接用来确认整套 RISC-V/Linux 语义都由模型从零编写。[原文其他案例与脚注 7](https://www.anthropic.com/research/formal-verification)

解释器的附录定理要求：**如果解释器返回结果，结果就符合所选形式语义**。形式语义与 CPython 的对应另用测试检验；约 170 万个程序上的 99.95% 一致率属于经验结果，不能读成对所有 Python 程序的等价证明。[附录第 2–3 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf)

@@opinion-begin@@

将功能条件写成断言，能把它接到“不发生规定的失败”这个目标上。但读取入口时，仍要检查断言究竟比较了什么，以及哪些路径真正执行了检查。例如，编码与解码的回环要求可以同时涉及返回状态、长度和内容；只检查其中一项，就只能得到相应的一项保证。

解释器案例则展示了另一种常见结构：实现满足形式语义，有机器检查的证明；形式语义是否忠于真实语言实现，则由另一条证据链支持。把这两段关系分开阅读，才能知道证明覆盖到了哪里，也能准确理解测试仍在承担什么工作。

@@opinion-end@@

### 2.6 主实验怎样使用 Rocq，是否需要现成验证器与 SMT

公开主实验的检查流程以 Rocq 为核心：给定二进制映像与固定命题，编译代理提交的证明，再检查假设。检查镜像包含 Rocq、LPS 及相关库，并不携带额外的证明自动化；编译、sanitizer 插桩、映像提取和生成脚本仍然参与整个流程。[检查环境](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/docs/checking.md)

这条主线没有把“由现成源码验证器生成 VC，再交给外部 SMT”作为说明中的核心步骤。另一项 Rust 解释器实验则使用 Verus 与 Z3。因此，“Rocq 主实验的证明检查不以外部 SMT 为核心”与“全文所有实验都不用 SMT”是两个不同说法。[附录第 3 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf)

@@opinion-begin@@

较有冲击力的一点，是这条路线没有先要求人类把每个困难都做成一个精巧的专用求解器。模型可以面对操作语义写证明，也可以自己写工具生成重复内容。**把困难的工作交给模型，人类设计任务边界、检查接口和信任结构**，构成了这项工作的宏观风格。

这不等于“不使用任何工具”：Rocq 本身就是证明工具，编译器、sanitizer 和脚本也不可缺少。这一设计带来的启发是，研究一个目标时，可以先思考能否直接为强模型提供正式语义、明确目标和可检查的反馈，再评估哪些部分确实需要额外自动化。

@@opinion-end@@

## 3. 兴奋与压力：模型能力、证明复用和成本

### 3.1 十亿行是尝试规模，行数不等于模型输出量

附录报告，尝试过程中产生约十亿行 Rocq，其中约 1.8 亿行属于成功证明。大量内容由工具和脚本生成，单个证明的检查也需要明显的计算时间。因此，不能用文件行数直接推算 API 输出费用。[附录第 3–4 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf)

@@opinion-begin@@

证明代码量说明完成证明可能需要处理多少细节，但它不是单独的质量指标。一个长证明可能记录了大量机械执行步骤；一个短证明也可能借助了定义良好的抽象。比较方法时，更有意义的是完成了什么性质、花了多少总资源，以及程序变化后有多少成果能够继续使用。

几亿行甚至十亿行的规模，也说明这条路线愿意用大量机械劳动换取可以检查的结果。对模型而言，重复展开细节可能是可行策略；对人类而言，这种证明方式很难长期手工维持。粗暴的方法开始可用，本身就会改变研究问题的选择和方法的评价方式。

@@opinion-end@@

### 3.2 图 4：较强模型用更少 token 到达同一完成率

*原文图 4。横轴为每个代理的 token 预算，纵轴为 36 个验证任务的完成比例；橙、蓝、灰分别对应 Opus 5.5、Fable 5.1 和 Opus 5。曲线越靠左，达到同一完成比例所需 token 越少。每题有三次独立尝试，每次上限 500 万 token；题目在首次成功时计为完成。这是小任务比较实验，不是 239 个入口的总预算。[原图](https://www-cdn.anthropic.com/images/4zrzovbb/website/02207cbc6f46e272fe9a0fa7929cb8ec29578e74-1920x980.png)*

这些小任务由真实入口缩减而来，使用简化运行时和 mini-ASan，输入限制为 64 字节；不能把图 4 的结果直接当作完整 OSS-Fuzz 项目的成本曲线。[附录第 5 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf)

@@opinion-begin@@

这张图带来的压力很具体。新方法在某个模型上节省了一部分搜索，模型升级也可能完成同样的事情。一个方法能否继续成立，需要在当时足够强的通用代理上检验，并比较相同预算下的完整完成率。只和较弱模型或过时配置比较，很难看出方法本身的价值。

@@opinion-end@@

### 3.3 图 5：共享证明减少重复劳动

@@anthropic-figure-5@@

*原文图 5，默认展示内容完整的静态图，展开可播放原始 GIF。横向按任务完成顺序排列，橙色弧线连接复用了相同文件的证明；向下的柱表示成功所需 token，黑色短横线是相应任务由独立代理完成的平均消耗。深蓝表示比独立运行更省，浅蓝表示没有更省；图中两项标注为独立运行未完成。[原始 GIF](https://www-cdn.anthropic.com/images/4zrzovbb/website/5078468fa7e09774b1ab6e86984ec5691d3d11fa-1080x712.gif)*

@@opinion-begin@@

这张图把两个需要分别测量的量放在一起：上半部分显示发生了复用，下半部分显示复用条件下的成本变化。共享了多少文件并不自动等于节省了多少计算；加载、判断和改写别人证明的时间，也应进入总账单。

共享工作区的价值还需要可靠的成果身份。后来者需要知道某个引理的准确陈述、依赖的模型版本、是否已通过检查，以及修改后还剩哪些义务。目录里存在一个文件，只表示有一份候选成果；完成检查后，它才成为可以依赖的证明。

@@opinion-end@@

### 3.4 图 6：不同项目的证明为什么大面积相似

[![Anthropic 原文图 6：libcups、freerdp 和 libzmq 的证明组成与复用程度](../assets/papers/anthropic-verification/figure-6.png)](../assets/papers/anthropic-verification/figure-6.png)

*原文图 6。三列分别是 libcups、freerdp 和 libzmq 的完整证明，块的高度按各部分字节占比绘制。深蓝为完全相同，浅蓝为小幅修改，浅棕为更多修改，橙色为新增；浅改的判定采用相同文件且大小变化在 2% 内。右侧标出分配器、sanitizer 运行时、共享库、规约以及普通和插桩构建等部分。颜色反映文件复用程度，不是语义等价的测量。[原图](https://www-cdn.anthropic.com/images/4zrzovbb/website/8e295614d599d548fbd2ff97ed3cc3e62f501b2b-1920x1248.png)*

@@opinion-begin@@

一份完整进程的证明，要处理许多与具体业务无关的启动和运行时行为。因此，库本身很小，也可能需要很大的证明。图 6 显示了把这些重复部分积累成基础设施的机会。

直接复制已经能带来帮助，但规模继续增加以后，经过明确接口封装的模块更有价值。调用者需要依赖一个可检查的契约，让底层实现的证明可以被引用；这样才有机会把“复制以后再证明”变成“使用已有结论，只证明新增部分”。

@@opinion-end@@

### 3.5 总成本需要完整账单，生态路线图依赖增长假设

Theorem 的另一篇[软件栈路线图](https://theorem.dev/blog/verified-software-stack/)采用每 KB 机器代码约 40 美元等起始参数，并假设验证能力持续快速增长，以估算 Nix 软件生态的验证进度与费用。这些是路线图的建模参数和预测，不能作为本次主实验的实际账单。

**表 2：规模、预算与价格分别指什么（本文整理）。**

| 数字或预算 | 对应对象 | 应怎样理解 |
| --- | --- | --- |
| 123 个库、239 个入口 | 主实验报告的完成范围 | 正文与附录未披露完整美元账单 |
| 每题三次、每次 500 万 token | 36 个缩减验证任务的模型比较 | 是尝试预算，不是主实验总用量 |
| 约十亿行、其中约 1.8 亿行成功 | 尝试过程与最终成功证明 | 含工具生成内容，不能直接折算输出 token |
| 每 KB 机器代码约 40 美元 | Theorem 生态路线图的起始参数 | 是模型参数，不是本次实验的结算单价 |

表 2 的四行分别统计交付范围、单次尝试上限、文本产物和预测参数。它们的分母不同，不能相乘后当成实际项目成本。图 4 的小任务结果，支持对模型效率的比较；软件生态能否以相同趋势降本，还取决于后续任务的复杂度与复用程度。

@@opinion-begin@@

成本评估至少要区分证明生成、失败尝试、证明检查、语义开发和补丁审查。成功案例的平均生成成本很有用，项目整体的完成成本也同样重要。两种统计分别回答“证出来一次多贵”和“把这些任务交付出去多贵”。

十亿行的规模容易引出百万美元级成本的猜测。但这个猜测没有完整 token 和计算账单作支撑，不能写成实验结论。几十美元每 KB 对工业项目可能有吸引力，验证大量依赖时也可能累积成显著开销；不能仅凭一个单位价格判断学术团队能否负担。

对于方法研究，还应报告固定时间、固定 token 和固定费用下的结果。较省 token 的模型可能具有不同的单价；证明检查耗时也可能成为新的瓶颈。最终应比较完成同一保证所需的总资源。

@@opinion-end@@

## 4. 什么值得信任：从证明检查到现实对应

### 4.1 证明文本可以不逐行阅读，信任基础仍要具体

公开检查流程会核对二进制哈希，从源文件编译证明，并生成独立包装定义，要求提交的证明具有指定陈述的类型；随后检查 `Print Assumptions`。仓库列出允许使用的公理，拒绝额外假设和未完成证明。默认检查使用 Rocq 内核；`rocqchk` 是可选的第二次检查。[证明检查流程](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/docs/checking.md)

信任基础还包括 ELF 到内存映像的工具、读取映像的插件、检查包装和假设解析程序，以及实际使用的 LPS 定义。检查器确认一个形式命题有证明；这些外围环节决定该命题是否对应预定的验证目标。[信任基础文档](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/docs/trust.md)

**表 3：需要分别审视的环节（本文整理）。**

| 环节 | 关键问题 | 审视对象 |
| --- | --- | --- |
| 需求与规约 | 命题是否包含实际需求 | 陈述、前提、输出与错误定义 |
| 执行语义 | 模型是否忠于目标机器和系统 | 指令、系统调用、启动与环境模型 |
| 软件产物 | 证明指向的是否是这份二进制 | 哈希、映像、版本与依赖 |
| 证明检查 | 证明是否依赖额外假设或错误目标 | 内核、允许公理、独立包装与审计 |
| 实际部署 | 部署条件是否满足定理前提 | 架构、链接方式、并发与资源限制 |

表 3 展示了一条从需求到部署的证据链。证明检查主要约束第四行，二进制哈希帮助固定第三行；它们不能单独完成第一、二、五行的工作。判断一份证明能否服务于真实系统，需要把这些环节接起来。

@@opinion-begin@@

形式化方法的价值之一，是把“相信整个生成过程”分解成可以明确列出的信任义务。生成证明的模型可以犯错，编写证明的策略也可以很笨；只要检查链可靠，错误候选就无法成为最终证据。

这项工作的一项核心局限，是它对 LPS 的信任仍然很重。对既定语义和规约的形式证明可以成立，语义与真实 Linux、真实指令执行之间仍可能有缺口。这个缺口不会因为模型生成了更多证明而自动缩小。

从找 bug 的工程目标看，可以把经过充分测试、范围明确的形式化当作一种可用假设，先让前沿模型在上面工作，再用真实执行确认产出的反例。但“这种假设可能已经足够有用”仍属于工程判断，不能替代它自身的正确性证据，也不能直接升级成整个系统可靠的结论。

但同一个可靠检查器，也能忠实地检查一个写错的目标。把关键性质变弱、把失败情况排除在前提之外，或者把程序换成另一个版本，都可能让证明更容易。目标固定、产物固定、假设可审计，和证明生成能力同样重要。

@@opinion-end@@

### 4.2 机器模型的缺口会成为结论的边界

LPS 的范围说明列出了单线程、静态可执行文件、信号处理及文件系统等限制，也列出了若干未检查的外部假设。文档特别说明：某些模型中过宽的非确定行为，会影响两个程序行为集合的等价比较；模型内的等价不一定自动转移到真实系统。[LPS 范围与已知缺口](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/SCOPE.md)

@@opinion-begin@@

这里有一个值得单独记住的区别。对“任何执行都不会出错”这样的全称安全性质，适当的行为过近似可以给出保守保证；对“两份程序的行为集合相等”，两边都增加模型特有的行为，可能改变相等关系。验证语义是否合适，取决于要证明的性质，不能只看模型包含了多少行为。

因此，共享机器语义值得长期投入。它一旦出错，许多证明会共同继承问题；它一旦得到修正，许多项目也会共同受益。需要积累的成果包括明确的适用范围、差分执行记录、与参考语义的对应证明，以及版本变化后哪些结论需要重查。

@@opinion-end@@

### 4.3 直接验证二进制，仍然需要跨越模型与现实

附录解释，直接把测试翻译成 Rocq 可能引入翻译错误，源码解释器也可能偏离实际编译结果，因此项目选择解释编译后的二进制。[附录第 1–2 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf)

@@opinion-begin@@

这是一种信任义务的安排。源码翻译路线要解释原程序与形式模型的关系；二进制路线要解释机器模型与目标平台的关系。前者通常保留更多高层结构，后者直接指向特定可执行文件。两条路线都需要给出清楚的对应关系。

如果研究目标是验证现有 C 程序，构造可执行的 Rocq 模型仍然有意义。关键是让转换过程保留所关心的执行：正常返回、运行错误和可能的发散都应得到适当处理。大量差分测试能够暴露翻译错误；要把模型证明提升为原程序保证，还需要经过论证的语义对应。验证时悄悄丢掉错误执行，会让模型看起来比原程序更安全。

@@opinion-end@@

### 4.4 自动修补以后，被证明的程序已经改变

原文允许 Claude 修补证明过程中发现的问题，再为新程序重新生成目标；脚注同时讨论了修改程序以迎合目标的风险，并介绍了补丁惩罚、行为变化奖励和日志审计。[原文脚注 6](https://www.anthropic.com/research/formal-verification)

@@opinion-begin@@

“修补后的程序满足性质”不包含“补丁符合维护者意图”。如果代理通过拒绝全部输入来消除崩溃，那么安全目标可能完成了，软件功能却被削掉了。补丁评估需要独立要求：原有合法输入是否仍然成功，输出是否保持预期关系，行为变化是否限制在应当修复的范围内。

同样地，已证明的二进制和原始版本应有清晰记录。读者应能知道哪些结论适用于原程序，哪些依赖尚未合并的补丁。证明是修补后版本的证据，补丁本身则需要另一组证据。

@@opinion-end@@

## 5. 还有哪些研究方向：把成果变成可信、可复用的保证

### 5.1 规格生成需要独立的正确性与充分性评价

@@opinion-begin@@

**形式规约不必只长成传统前后置逻辑公式的样子。** 一个 fuzz 目标可以提供可执行的观察与失败条件；一个参考解释器、算法的抽象过程或状态转换系统，也可以描述期望行为。它们最终仍要形成明确的形式命题，但人类编写规约的入口可以更丰富。

以一个参考算法作规约，可以要求实现与它返回相同结果；以抽象状态机作规约，可以要求实现产生的可观察行为被抽象机允许。一个 fuzz 目标能否提供有用规约，则取决于其中检查是否对目标错误敏感。关键是怎样定义行为、输入范围与比较关系，而不只是选用什么表示语言。

证明容易获得以后，“应该证明什么”会更加突出。对于解析器，合法输入的接受范围和输出含义值得写清；对于权限检查，应约束哪些操作必须被拒绝；对于数值程序，应说明误差、溢出和特殊值的处理。

从代码生成规约时，最大的陷阱是评价的循环。若唯一标准是“原代码能满足生成的规约”，那么恒真条件、遗漏错误分支的前提，甚至只重复实现的描述，都可能得高分。实现提供线索，却不能同时充当需求是否正确的唯一裁判。

可以用独立需求、参考模型、人工审查和变异程序来检验规约。以排序为例，输出有序仍不足以排除丢元素；再要求保留输入的多重集合，才能约束这类错误。若一个已知违反需求的变异实现仍满足规约，就获得了规约漏项的具体证据。反过来，拒绝若干变异体，也只说明挡住了这些错误，不能自动证明规约完整。

操作系统也是一个值得尝试的方向：由人给出相对简洁的抽象状态转换，让模型寻找实现状态与抽象状态之间的关系，提出不变量，并完成行为对应的证明。这样有机会减少人工搭建精化证明的负担。不过，只要目标仍是“实现满足这个抽象规范”，状态对应、允许行为和环境假设这些义务就仍然存在；模型可以替人完成它们，不能靠换一种表述让它们消失。

@@opinion-end@@

### 5.2 让模型 formalize，再测试 formalization，能走多远

@@opinion-begin@@

源码级、IR 级和二进制级验证可以服务于不同的工程目标。值得持续投入的是把它们之间的关系讲清并检查：源程序的哪些执行被模型保留？目标程序增加了哪些假设？一个层面的安全结论满足什么条件才能传递到另一个层面？

沿着这项工作的宏观思路，还可以尝试：**让模型把现有代码 formalize 到 Rocq 或 Lean，先对这份可执行形式化做充分测试，再在其上证明功能性质。** 在明确接受“形式化正确”这一工程假设后，这可能成为一条成本更可控、保留高层结构的路线。

测试的对象可以是原程序与形式模型的输入输出、关键中间状态和错误行为；证据也应包括已知边界、失败案例和支持的语言子集。这样做并不能把假设变成定理，却能帮助界定这份模型可接受的使用范围。要宣称对原程序的严格保证，仍需额外的对应论证。

对浮点 C 程序，这种关系必须具体到数值表示和执行规则。实数模型能帮助表达数学意图，却不能仅凭同样的公式代替浮点实现；舍入、NaN、无穷大、有符号零，以及编译选项，都可能影响行为。若选择受限子集，也应让支持范围成为结果的一部分。

错误执行同样需要进入对应关系。一个模型若只保留正常返回的输入，证明它所有返回值都正确，可能完全没有处理原程序上的非法访问或异常路径。有界检查、差分执行和形式证明可以各自提供证据，但必须清楚说明每一种证据覆盖的范围。

证明有望逐步替代一部分针对固定性质、固定软件产物的重复测试，使更多精力能够集中到检查共享 formalization 和构造功能规约上。不过，反例的真实重放、模型与实现的对照、部署环境的变化仍然需要检验。“在模型里证完了”不会自动让所有代码测试都失去意义。

@@opinion-end@@

### 5.3 模块化抽象需要证明它能改善后续任务

@@opinion-begin@@

强模型能够补很多执行细节，但好抽象依然有机会减少工作。一个分配器契约、调用约定或分离逻辑规则的价值，不只在于把当前证明缩短，还在于让后续程序在明确前提下直接使用它。

这类工作的评估可以跨程序、跨版本进行：新项目少花多少预算？实现变化以后，多少证明仍然有效？替换模型后，抽象带来的收益是否保留？引入抽象是否增加了人工规约负担？这些问题更接近证明基础设施的实际价值。

@@opinion-end@@

### 5.4 评测要同时约束目标、实现和资源

@@opinion-begin@@

**表 4：值得长期跟踪的研究问题与证据（本文建议）。**

| 研究问题 | 更有说服力的证据 | 需要防止的评测漏洞 |
| --- | --- | --- |
| 规约是否忠于需求 | 独立需求审查、漏项反例、变异检验 | 只按原实现能否证明来评分 |
| 模型是否对应实现 | 执行对照、对应定理、错误路径保留 | 静默排除模型不支持的执行 |
| 证明能否可靠复用 | 固定依赖的新任务与跨版本实验 | 共享文件存在却没有完成检查 |
| 补丁是否保持功能 | 合法输入行为、变化范围与回归证据 | 通过删功能完成安全目标 |
| 方法能否持续节省成本 | 强代理基线、完整成功率与总账单 | 只报告成功尝试或较弱基线 |

表 4 把未来工作的价值落实到可以交付的证据：规约用独立要求评价，形式化用执行和对应关系评价，证明系统用完整交付与总成本评价。最需要防止的是，让同一个生成过程同时决定需求、程序、规约和验收规则，最后只报告“全部通过”。这些环节可以使用同类模型辅助，但关键目标和检查方式必须具有独立约束力，并记录每一次有意义的改变。

@@opinion-end@@

### 5.5 更强的模型，要求更准确的保证表述

@@opinion-begin@@

Anthropic 的这篇文章让人兴奋，因为它展示了大量真实程序证明可以由模型持续推进。它也带来压力：一些曾经需要专门方法安排的局部证明行为，正在成为通用代理的能力。人类把握宏观设计、模型承担繁重形式化与证明的工作方式，已经值得认真尝试。

这项工作可视为一条很有力量、同时承担了明显信任假设的工程路线。它没有一次解决软件正确性的全部问题，但能够交付被实际确认的漏洞，就已经有直接价值；在给定语义和规约下完成的形式证明，也应当按其真实范围得到承认。

后续研究仍可推进许多具体工作：把需求写成有约束力的规约，把原程序与形式模型连接起来，把机器语义的缺口缩小，把一次性证明整理成可复用接口，把补丁和部署条件纳入证据链，并建立能够经受模型升级的评测。

**值得信任的是陈述准确、前提明确、产物可定位、检查过程可复现的证据。** 模型越能写证明，规格与现实之间的距离就越值得研究。证明规模已经开始改变；接下来要争取的，是保证的范围、可信程度和交付成本也一起改善。

@@opinion-end@@

## 6. 源码里的 spec 与 LPS：命题究竟如何落到二进制上

以下核对固定到公开证明仓库的 `98e995d4` 与 LPS 的 `f1006fe8`，避免将后续版本混在一起。代码片段分别注明原样节选与解释性示意；定义存在、命题被证明、命题适用于部署程序，是三个需要分别核对的状态。

### 6.1 真实 spec：cJSON 的两条 Rocq 定义

[`projects/cjson/cjson_read_fuzzer/Statements.v`](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/projects/cjson/cjson_read_fuzzer/Statements.v) 中有以下定义，原样节选并调整换行：

```coq
Definition plain_halts : Prop :=
  halts_within_budget
    Budgets.Standard.lim_source
    Exits.ok_or_refused
    Images.plain.

Definition asan_agrees : Prop :=
  agrees_in
    Env.alloc_forced_only
    Budgets.Asan.lim_source
    Budgets.Asan.lim_target
    Images.plain Images.asan.
```

这里的 `Prop` 表明它们是命题。第一条把终止模板应用于普通二进制映像，第二条把无错误且行为一致的模板应用于普通构建和 ASan 构建。具体含义取决于模板、参数和映像；两行调用很短，并不意味着完整定义或证明也很短。

**表 5：这个入口实际公开了哪些证明（按固定版本 README 整理）。**

| 命题 | 主要要求 | 查阅版本中的状态 |
| --- | --- | --- |
| `plain_halts` | 资源与环境前提下，普通构建以允许状态终止 | 开放目标 |
| `asan_agrees` | 两个构建无规定错误，有限可观察行为集合相同 | 已证明 |
| `ubsan_agrees`、`asan_ubsan_agrees` | 对相应插桩构建提出一致性与无错误要求 | 已证明 |
| 概率界和可判定性命题 | 针对输入分布的界，或识别一致输入的程序 | 开放目标 |

表 5 的状态来自该入口的 [README](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/projects/cjson/cjson_read_fuzzer/README.md)。其中还说明，入口会解析、打印和压缩 JSON 文本，但输出被释放，没有进一步比较内容。因此，这个例子的证明不能读成 JSON 解析与输出的完整功能正确性；已经完成的一致性证明也不能自动升级成尚未完成的终止证明。

@@opinion-begin@@

这是读取项目结果时很有用的一种顺序：先找具体入口，再看陈述，然后核对证明状态。仅看到一个命题写成 `Definition ... : Prop`，不能断言它已经被证完。即使入口调用了复杂算法，它是否有功能保证，仍取决于驱动程序实际观察了什么。

@@opinion-end@@

### 6.2 映像不是抽象函数，而是指定 ELF 的加载结果

[`Images.v`](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/projects/cjson/cjson_read_fuzzer/Images.v) 给普通构建的定义是：

```coq
Definition plain : Image :=
  mkImage
    Plain.M.loaded_segments
    Plain.M.init_pc
    Plain.M.phdrs.
```

三个参数分别来自该二进制的可加载段、入口地址和程序头信息。底层段数据由 `elf-snapshot` 在构建时生成；[`harness.yaml`](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/projects/cjson/cjson_read_fuzzer/harness.yaml) 则记录源版本、构建和二进制 SHA-256。映像还要检查良构性，排除“根本没有合法启动状态，所以全称命题空泛成立”的情况。

这个驱动会读取输入文件并调用 fuzz 入口。参数错误、文件不可读、头部不完整或文件达到 64 MiB 时，可以直接返回状态 2。允许的正常退出集合包含 0 和 2，因此“退出状态合法”不要求每个文件都成功进入库函数。各构建还固定了部分环境函数的结果，例如 `getenv()` 返回空指针、`getpid()` 返回 1。这些细节也属于被验证程序的身份。[入口与驱动说明](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/projects/cjson/cjson_read_fuzzer/README.md)

@@opinion-begin@@

这也解释了为什么证明必须绑定软件产物。模型证明的是这些段里的指令及其允许的运行环境；源代码仓库里的相同文件名，不能替代二进制身份。驱动拒绝输入本身可以是正确行为，但要确认它没有把原本需要处理的正常输入排除掉。

@@opinion-end@@

### 6.3 展开 spec：量词、环境、内存前提和结论

[`Shapes.v`](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/theories/Shapes.v) 中，一致性模板的前提包括以下原样节选；省略号表示后续结论未在代码块中展开：

```coq
valid_entry plain en_plain inp ->
valid_entry san en_san inp ->
valid_input inp ->
~ run_scfg_budget_refused
    env plain lim_plain
    en_plain inp ->
...
```

外层对两个构建的启动布局和进程输入分别全称量化。进程输入包括参数、环境变量、初始文件、标准输入等；启动布局包括栈、堆起点和相关随机字节。两个构建的布局不必相同。前提成立后，要得到普通构建无错误、插桩构建无错误，以及两者有限轨迹集合相同。

用缩略记号表示这一结构，以下是解释性公式，并非仓库代码：

$$
\begin{aligned}
&\forall e_p,e_s,i,\\
&\quad\operatorname{Valid}_p(e_p,i)\land\operatorname{Valid}_s(e_s,i)\\
&\quad\land\operatorname{ValidInput}(i)\land\operatorname{BudgetOK}_p\\
&\qquad\Longrightarrow\operatorname{ErrorFree}(R_p)\\
&\qquad\qquad\land\operatorname{ErrorFree}(R_s)\\
&\qquad\qquad\land\operatorname{Traces}(R_p)=\operatorname{Traces}(R_s).
\end{aligned}
$$

其中 $R_p$、$R_s$ 是对应环境、预算、布局和输入下的运行。cJSON 的 ASan 一致性目标采用普通构建 2 GiB、插桩构建 512 GiB 的预算；普通终止目标另用 16 GiB。`alloc_forced_only` 要求内存请求只在预算耗尽或找不到可用地址范围时失败，其他种类的请求仍可能失败。它们是不同命题的参数，不能混成一个统一资源保证。[参数与模板定义](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/theories/Shapes.v)

@@opinion-begin@@

真实 spec 的复杂性主要藏在这里。用中文概括为“所有输入都不崩溃”很方便，但允许哪些环境失败、预算条件放在哪个构建上、轨迹怎样比较，都会改变证明难度和结论范围。检查这些前提，比单看定理名称更能判断保证是否适用。

@@opinion-end@@

### 6.4 LPS 的源码结构：指令、机器状态、系统调用与整体行为

**表 6：从 spec 向下阅读 LPS 的主要文件。**

| 文件或目录 | 定义什么 | 与证明目标的关系 |
| --- | --- | --- |
| `Riscv/Instr.v`、`Decode.v`、`DecodeC.v` | 指令语法及普通、压缩指令解码 | 识别映像中的机器指令 |
| `Riscv/Sem.v` | 指令对核心状态产生的效果 | 给算术、跳转、访存等指令含义 |

| `Run.v` | 进程转换关系、运行轨迹和错误 | 形成可供安全性命题引用的整体行为 |
| `EquivalenceDefinition/` | 行为一致、终止等性质 | 给 spec 提供通用命题模板 |

表 6 展示的是语义层次，而不是七个独立验证器。可以从具体映像沿解码、执行、系统调用一路读到整体行为，再回到上层 spec。[LPS 仓库结构](https://github.com/theorem-labs/rocq-linux-process-semantics/tree/f1006fe8178338a499b5e5c41be83006c4edd058/theories)

机器状态的几个字段如下，来自 [`RiscvSemantics.v`](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/LinuxProcessSem/RiscvSemantics.v)。这是省略其他字段的结构节选，不是可直接编译的完整定义：

```coq
Record machine_state := {
  ms_regs : bvmap 5 word;
  ...
  ms_pc_val : word;
  ...
  ms_mem : word -> option byte;
  ...
}.
```

寄存器文件、程序计数器和按地址查询的字节内存是其中一部分；完整状态还含浮点寄存器、待处理系统调用和只读内存等。指令语法也是真实的 Rocq 数据类型，例如 [`Instr.v`](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/Riscv/Instr.v) 用构造子区分加载、存储、跳转和运算。随后由解码与执行定义解释这些对象。

@@opinion-begin@@

因此，“直接在 Rocq 里证明二进制”并不省略程序语义。这个过程明确建立了一套机器与进程模型。它把源语言前端的复杂性移出了每个项目的证明入口，却仍需要承担目标架构、运行时和系统环境的复杂性。

@@opinion-end@@

### 6.5 一步如何执行，系统调用为什么是非确定的

[`Sem.v`](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/Riscv/Sem.v) 将解码后的指令与核心状态映射到效果对象。访存效果交给机器层解释；系统调用则交给进程层处理。LPS 的 [`Specs.v`](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/LinuxProcessSem/Specs.v) 用以下定义选择相应系统调用规约：

```coq
Definition syscall_spec
  : Sys SyscallEffect :=
  dispatch spec_table.
```

一个系统调用规约可以允许多个结果，例如读取部分可用字节，或在所选环境允许时返回失败。实际效果包括返回值、写入内存的字节，以及映射、清零等变化；进程转换关系再将允许的效果应用到状态。这里需要证明的是所有许可分支，而非一次解释器运行所选择的分支。[系统调用效果](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/LinuxProcessSem/State.v)

因此，一步进程执行可以按下面的流程理解。这是阅读源码后的解释性示意，不是 Rocq 原码，也不是完整实现：

```text
进程状态
  → 按程序计数器取指、解码
  → 解释指令，更新状态
  → 系统调用：选择许可结果
  → 产生下一状态与可观察事件
```

这条流程在源码中被拆成机器步进、系统调用处理和 `sstep` 转换关系；最终的运行行为则收集任意有限步数所能产生的轨迹。[步进与运行关系](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/LinuxProcessSem/Run.v)

机器层还区分正常结果、程序故障和模型未覆盖的情形。后两者都妨碍相应的无错误目标成立，但诊断意义不同：非法访存可能是真实错误，未支持的指令或系统调用也可能只是模型边界。这个区别保存在进程执行定义中。[机器结果与进程转换](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/LinuxProcessSem/Run.v)

### 6.6 整体行为是什么，证明文件又交付什么

[`Run.v`](https://github.com/theorem-labs/rocq-linux-process-semantics/blob/f1006fe8178338a499b5e5c41be83006c4edd058/theories/LinuxProcessSem/Run.v) 的整体行为记录如下，原样节选：

```coq
Record behavior := mkBehavior {
  bh_traces : list event -> Prop;
  bh_errors : Prop;
  bh_all_errors : Prop;
  bh_unmodeled : Prop;
}.
```

第一项表示有限事件序列的集合；其余项目分别记录是否存在错误执行、是否所有执行都进入错误，以及是否存在到达模型未覆盖部分的执行。集合式行为为非确定执行提供了表示，也说明仅比较某一条具体运行轨迹远远不够。

证明文件最终要交付一个具有固定 spec 类型的证明项。检查程序独立生成包装定义，把候选证明放到指定目标的类型下，再审计依赖假设；目标被偷换时，正确类型也应匹配失败。[证明交付格式](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/docs/proving.md)、[检查流程](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/docs/checking.md)

@@opinion-begin@@

短 spec 背后是一整套可执行对象与行为定义。Rocq 检查了相对于这些定义的证明；定义是否准确描述真实程序，仍是信任基础的一部分。源码能够把这项义务具体定位出来，却不会仅因“定义也写在 Rocq 中”而自动证明其现实对应关系。

@@opinion-end@@

## 7. 六页附录逐节解读：正文之外还需要知道什么

附录没有另外编号的图表，但有六个主题和一段 LZO 代码。以下依原顺序补充其含义；前文已经展示的六张图仍按正文顺序排列。

### 7.1 三项义务：为什么一致性之外还要分别排除错误

附录先要求 ASan 构建无错误，再比较它与普通构建的可观察行为，最后单独排除普通构建的错误。观察对象包括标准输入读取、标准输出和错误输出写入、退出状态或终止信号，以及最终文件系统；性能不在这个比较范围内。错误则包括故障、主动中止和语义未覆盖的行为。[附录第 1–2 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf#page=1)

这个拆分有实际原因：有限轨迹本身没有单独记录 crash，一个程序发生错误、另一个进入不再产生事件的死循环，可能仍具有相同的有限观察。因此，不能只靠轨迹相同，就把一个构建的无错误性质传给另一个。§6.3 的公开模板把两个 `error_free` 与轨迹一致性明确合在同一命题中，但终止仍是另外的目标。

@@opinion-begin@@

这是阅读“一致性证明”时最应检查的细节之一：一致的是哪些观察，错误与不终止怎样进入定义，结论是否足够强。一个关系名称叫 equivalence，并不意味着它自动保留所有关心的性质。

@@opinion-end@@

### 7.2 Python 解释器：部分正确性与现实对应分开建立

解释器实验采用 safe Rust、Verus 和 Z3，按基于 λπ 的形式语义完成 17 个层次的证明。结论约束返回结果；与 CPython 的对应由测试检验。作者另外向早期版本注入七个错误，其中五个通过了随机测试，七个都使证明失败。选择 Verus 有 Rust 生态与实验安排方面的原因，并非只能用这一种证明系统。[附录第 2–3 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf#page=2)

@@opinion-begin@@

这组结果说明证明可能发现测试遗漏的错误，同时也展示了信任边界：实现与形式模型之间有证明，形式模型与 CPython 之间有经验比较。若形式语义漏掉了需求，前一项证明仍可能全部成立。人工注入错误的结果也应按这七个案例理解，不能外推为所有缺陷的检出率。

@@opinion-end@@

### 7.3 大量证明究竟花在哪里

附录用 cJSON 说明规模反差：391 行解析入口对应约 63 万行证明，只有约十分之一围绕 cJSON 本身；链接约 5.1 万行代码的 fftw3 对应约 48 万行证明。典型交付约 60 万行、1,400 个文件，不同库的证明约为 33 万至 90 万行。启动过程、分配器、输出函数、ASan 运行时和驱动都要处理，当时的证明还不能直接导入这些共同结果。超过一半的文本由代理编写的工具生成；检查一个证明可消耗半小时到数小时 CPU 时间。[附录第 3–4 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf#page=3)

@@opinion-begin@@

库代码少，不代表进程行为简单。证明行数在这里混合了目标库、运行环境、生成数据和重复工作；这些部分的成本应分别测量。复用若能同时减少生成、维护与检查成本，价值会比单纯缩短文本更直接。

@@opinion-end@@

### 7.4 专家怎么看：短规约、冗长证明与抽象能力

附录中的专家观察是，代理经常先写一个描述输出的短规约，再把两个构建分别与它联系起来；这类规约的中位数约 110 行，对应程序机器代码中位数约 86 KB，其中驱动实际涉及约 20%–50%。证明过程却反复展开寄存器、整数转换、地址互异、栈内容与各分支。代理也使用了 framing、布局无关推理和分配器抽象，但使用并不一致，证明规模改善仍有限。附录将更复杂程序上的规模扩展列为开放问题，并讨论了建立更好模块抽象的必要性。[附录第 4–5 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf#page=4)

@@opinion-begin@@

短规约的出现值得关注，但“两个实现都满足同一规约”本身并不足以推出两者行为一致。例如，一个程序输出 0，另一个输出 1，两者都满足“输出非负”。中间规约必须具有足够的区分能力，或配合更强的对应定理。最终应检查实际证明出的关系，不能只看规约长度。

冗长证明一旦通过同一目标的可靠检查，其逻辑效力不因写法而降低；抽象的价值主要体现在后续扩展、复用、调试和成本。能否自动找到合适的模块边界，比是否模仿人类的证明风格更值得验证。

@@opinion-end@@

### 7.5 图 4 的小任务与主实验相差在哪里

比较模型的 36 个任务分为三组，每组 12 个：从较小程序的插桩无错误，到更大程序，再到同时要求两个构建无错误且行为一致。实验将输入缩为 64 字节，以少量函数替代 libc，用约百条指令的 mini-ASan 替代大型运行时，最终程序为 283–2,491 条指令。[附录第 5 页](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf#page=5)

@@opinion-begin@@

这些任务能帮助比较模型在受控证明任务上的效率。把曲线换算成完整项目的报价，还需要补入真实运行时、输入范围、模型缺口、重试和证明复用的影响。任务缩减方式属于结果解释的一部分。

@@opinion-end@@

### 7.6 LZO 断言：安全性目标怎样携带功能要求

附录第 6 页展示压缩后再解压的代码。以下原样摘出控制分支和两条断言，调整换行并省略实际函数调用，因此不是完整程序：

```c
assert(r == LZO_E_OK);
if (compressed_len >= size)
  goto join;
...
assert(r == LZO_E_OK &&
       decompressed_len == size);
```

第一条检查压缩成功；当压缩结果小于原输入时，后续分支解压并检查成功状态及还原长度。断言失败会进入中止路径，因而排除 crash 的证明也覆盖这些要求。附录还以 p11-kit 的 PEM 块长度检查说明：维护者写在入口中的约束，可以直接成为证明需要排除的失败分支。[附录第 6 页代码与说明](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf#page=6)

@@opinion-begin@@

这个例子纠正了“安全性完全没有功能内容”的笼统说法。入口断言可以要求算法返回成功并恢复正确长度。不过，展示的片段没有比较解压字节与原输入；仅依据这些断言，不能将结论扩大成完整的逐字节往返正确性。进一步的功能保证，要落实到完整入口、实际 spec 和已完成的定理上。

@@opinion-end@@

## 8. 找 crash、证明无 crash 与完整内存安全：从一次越界写说起

### 8.1 到底在找什么 bug：先看入口怎样失败

主实验把库、fuzz 驱动与插桩运行时编译成程序，寻找能使这个程序进入规定错误的输入。失败可能来自普通程序自身的故障，也可能来自 ASan 报告后中止，或入口中的断言失败。模型不支持的行为也被纳入证明要排除的错误，但单凭模型无法继续执行，还不能确认真实程序有漏洞；需要诊断并重放。

原文举出的一个例子是：某个解压器只有在约 20 MB、布局特殊的输入下才出现计数器下溢，进而发生越界写。这说明证明过程中寻找输入，可以触及常规 fuzzing 很难碰到的组合条件。原文主实验的最终目标是修补后完成指定入口的无 crash 证明；寻找漏洞也是即使未能证完仍可交付的成果。[原文的漏洞发现与实验目标](https://www.anthropic.com/research/formal-verification)

**这里的 crash 是检查程序的失败信号，不能与所有软件错误画等号。** ASan 可以把某些原本暂时不崩溃的内存错误变成报告与中止；维护者也可以用断言把算法要求变成失败分支。§7.6 的 LZO 示例检查成功状态与还原长度，就是后一种情况。入口没有观察的功能要求，不会仅因为“入口不崩溃”就自动得到验证。

@@opinion-begin@@

对找 bug 的目标，最有说服力的交付物是能够真实复现、并违反预期契约的输入及执行过程。证明失败只是线索；证明成功和漏洞复现则是两种不同的成果。报告结果时，把它们分别计数，能够更准确地体现这条路线的价值。

@@opinion-end@@

### 8.2 ASan 做了什么：越过箱子边界，不一定撞到仓库的墙

可以把进程的可访问地址空间想成仓库，把一次分配得到的缓冲区想成箱子。操作系统的页级保护通常不会为每个小对象单独立墙：写出了箱子，却还在可写的仓库区域里，程序可能暂时正常运行，只是已经破坏了数据。

ASan 通过编译时插桩与运行时库，为许多内存访问增加检查，并用影子内存记录地址是否允许访问。可以把它理解为在部分边界和失效区域布置警报。某次访问命中禁用区域，便报告错误并通常中止程序；这些机制并不等于完整跟踪所有对象归属与语言层面的内存合法性。[ASan 的组成与工作方式](https://clang.llvm.org/docs/AddressSanitizer.html)

例如，假设驱动分配了 16 字节的堆缓冲区 `p`，输入控制索引 `i`，随后调用这个解释性示例；它不是论文项目中的原码：

```c
void put(char *p, size_t i) {
    p[i] = 1;
}
```

`i == 16` 时，尝试写入的是第 17 个字节。普通构建可能破坏邻近数据而没有立即崩溃；在 ASan 构建中，如果目标地址被标记为禁用区域，相应检查会报告越界并中止。于是，一个原本可能静默的内存错误，被转换成 fuzz 驱动与无错误命题能够观察到的失败。

```text
输入控制索引
  → 执行一次写入
  → ASan 检查目标地址
  → 命中禁用区域，报告并中止
```

对某个输入运行一次，能够发现这次执行中的报告；形式证明进一步尝试排除前提范围内所有执行的这种失败。两者使用同一类可执行检查，但覆盖的量词不同。证明的是指定二进制中实际存在的检查，而非任意版本、任意配置的 sanitizer 都不可能报告。

### 8.3 三种结论的量词和依据不同

**表 7：找 crash、无 crash 保证与完整内存安全的区别。**

| 目标 | 需要交付什么证据 | 不能直接推出什么 |
| --- | --- | --- |
| 找到并确认一个 crash | 一个输入和相应环境，在真实目标上复现规定失败，并确认违反预期契约 | 其他输入是否安全 |
| 指定插桩构建无 crash | 对前提允许的全部执行，排除该构建中的规定错误，并建立模型与真实执行的对应 | 所有 sanitizer 都不报错、所有内存错误都不存在 |
| 普通构建无 crash | 对普通二进制的全部允许执行，直接排除所定义的故障与中止等错误 | 没有静默内存破坏、没有错误输出、一定终止 |
| 完整内存安全 | 对明确的内存安全定义，排除范围内所有执行的相关违规，例如对象边界和生命周期违规 | 全部功能正确、不会主动中止或挂起 |

表 7 中的“全部”同时受入口、输入、内存布局、环境响应和资源前提约束；“完整内存安全”也必须先说明采用什么语言或机器层定义。**无 crash 与内存安全不是简单的线性包含关系：程序可以内存安全却触发失败断言，也可以越界写却暂时不崩溃。**

公开的 `agrees_in` 并非只要求 ASan 不报告。它还直接要求普通构建无模型错误。将其结论缩写，结构是：

$$
\begin{aligned}
&\operatorname{ErrorFree}_{M}(P)\\
&\quad\land\operatorname{ErrorFree}_{M}(S)\\
&\quad\land\operatorname{Traces}_{M}(P)
=\operatorname{Traces}_{M}(S).
\end{aligned}
$$

这里 $P$ 是普通二进制，$S$ 是指定插桩二进制，$M$ 是形式语义；外层量词和前提见 §6.3。既然普通构建的无错误性本身就在证明目标中，它不必通过“ASan 能捕获所有 crash”来间接获得。[实际命题模板](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/theories/Shapes.v)

如果只有“ASan 从不报告”这一结论，却要推出“任何内存错误都不存在”，则需要额外证明：每一种目标内存错误都会在相应插桩执行中被报告。现有 ASan 不提供这样的完整覆盖。普通构建无模型错误，也不能补上模型并未定义为错误的对象归属或子对象边界违规。[cJSON 陈述中的覆盖限制](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/projects/cjson/cjson_read_fuzzer/Statements.v)

@@opinion-begin@@

评价这项工作时，应分别承认三类价值：真实复现的缺陷、指定语义与前提下的无错误证明，以及进一步建立的功能或内存安全性质。把第一类成果贬成“没有完整保证所以没用”，会低估找漏洞的工程价值；把第二类成果直接写成完整内存安全，又会扩大它的证明范围。

@@opinion-end@@

### 8.4 形式化不可信，会影响哪一条结论

继续使用仓库的比喻：形式语义像一份描述通道、边界和警报器的地图。依据地图找到可疑位置，再到真实仓库确认确实出错，这个发现不因地图其他地方画错而失效。反过来，仅在地图上证明所有路线都安全，结论能否适用于仓库，就取决于地图是否保留了真实可能发生的危险。

```text
找 bug：
  模型提供候选输入
  → 真实目标复现失败

提供保证：
  模型内完成全称证明
  ＋ 模型与真实执行的可靠对应
  → 前提范围内排除规定错误
```

因此，错误或尚未充分验证的形式化，可能使寻找漏洞的过程遗漏真实错误，也可能产生无法复现的线索；但一个已经在真实目标上复现并确认的 bug，仍然有效。对于“所有允许执行都安全”，若模型漏掉真实执行、把错误当作正常结果，或错误处理了运行环境，则模型内证明不足以支持现实中的全称保证。

这里需要的是适合目标性质的语义对应。对全称安全性质，保守覆盖真实执行可以足够，并不要求模型中的每条行为都真实可发生；但不能悄悄丢掉真实错误。语义的依据可以由差分执行、独立审计和与参考模型的对应证明加强；通常的有限样本测试不能完成对所有执行的对应论证。§4.2 讨论了过近似对安全性和行为等价的不同影响。

还应区分语义与检查器：如果只有语义偏离现实，而 Rocq 检查链可靠，那么已检查的形式命题仍然成立，缺少的是将它应用到现实的依据。若检查链本身也不可靠，连模型内的证明结论都需要重新核验。[项目的信任基础](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/docs/trust.md)

@@opinion-begin@@

“形式化需要信任”不意味着只能凭感觉接受，也不意味着所有结果一并作废。更有用的做法是明确哪部分尚未建立对应、哪些已复现的发现不受影响、哪些无错误保证仍带着假设。找漏洞允许先采用有用但不完美的地图；提供保证则要交代地图与现实之间的证据。

@@opinion-end@@

### 8.5 ASan 会漏掉什么：地址可访问，不代表访问合法

**表 8：ASan 的典型盲区，以及其他检查的分工。**

| 情形 | 直观例子 | 覆盖边界或补充方式 |
| --- | --- | --- |
| 对象内部越界 | 数组成员越界，覆盖同一结构体中的后续成员 | 默认 ASan 未必区分内部成员边界；部分额外检查可补充 |
| 错误访问落入另一个活对象 | 本应写对象 A，算错地址后写进仍存活的对象 B | 地址可访问，不等于指针归属与访问意图合法 |
| 未插桩代码中的访问 | 库或汇编中的普通读写没有相应检查 | 拦截器可能覆盖部分操作，不能视为全面覆盖 |
| 超过逻辑有效长度 | 分配 1,024 字节，只有前 64 字节有效，却读取第 100 字节 | 分配边界内的访问可能不报；需要长度不变量或相应标注 |
| 使用未初始化值 | 根据未初始化变量选择分支 | 主要由 MemorySanitizer 检查 |
| 整数与其他未定义行为 | 有符号溢出、非法移位等 | 需要启用相应 UBSan 检查，并核对具体配置 |
| 数据竞争 | 两线程无同步地访问同一数据且至少一次写入 | 由 ThreadSanitizer 等检查；主实验限定单线程 |
| 功能或权限错误 | 输出内容不对，或遗漏权限检查 | 通用 sanitizer 通常不知道预期结果，需要功能规约或断言 |

表 8 的前三行涉及内存访问检查本身的缺口；后面还包含 ASan 不负责的其他性质。公开 cJSON 命题明确列出“访问落入另一个活对象”和“未插桩代码”两类限制。[项目中的明确说明](https://github.com/theorem-labs/oss-verify-proofs/blob/98e995d4daced70a0a4aa2c810854b88720735f1/projects/cjson/cjson_read_fuzzer/Statements.v) 容器内部逻辑边界可以通过专门标注增强检查；没有标注时，不能自动把分配边界理解为有效数据边界。[ASan 容器检查说明](https://clang.llvm.org/docs/AddressSanitizer.html#disabling-container-overflow-checks)

一个更容易看见的对象内部越界例子如下，同样是解释性示例：

```c
struct S {
    char data[8];
    int allowed;
};

void put_member(struct S *s, int i) {
    s->data[i] = 1;
}
```

在常见布局下，`i == 8` 可能写到 `allowed` 的字节。它已经越过 `data` 的数组边界，却仍处于整个结构体对象内部；默认 ASan 可能不报警。用箱子比喻，这相当于破坏了箱子内部的隔间，但没有碰到外侧警报。某些 UBSan 边界检查或额外布局插桩可以覆盖部分此类情况，不能据此宣称所有内部越界都被排除。[ASan 开发者对内部越界的说明](https://github.com/google/sanitizers/wiki/AddressSanitizerIntraObjectOverflow)

其他 sanitizer 也各有目标：[MemorySanitizer](https://clang.llvm.org/docs/MemorySanitizer.html) 关注未初始化值的使用，[UBSan](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html) 覆盖启用的未定义行为检查，[ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html) 检测数据竞争。启用了某个工具，不等于已经启用这个工具族里的全部检查；全部检查都通过，也不会自动生成业务功能要求。

@@opinion-begin@@

最需要避免的跳跃，是从“警报没有响”推到“所有错误都不存在”。证明能把指定警报在有限样本上的沉默，提升为前提范围内所有执行都不触发它；证明的量词变强了，警报本身的检测边界仍然存在。要进一步获得完整内存安全或功能正确性，就要把那些遗漏的要求真正放进模型与命题。

@@opinion-end@@

### 8.6 排除证据更强，不等于找漏洞的效率必然更高

@@opinion-begin@@

相对于有限次运行，一个完成的全称证明能够提供更强的排除证据。证明过程也可能帮助定位大输入、稀有分支和复杂调用历史中的错误。然而，这不推出它在所有项目、相同预算下都必然胜过直接让模型找漏洞或运行 fuzzer。

比较找漏洞能力，应统一入口、输入范围、构建与资源，比较确认缺陷的数量、失败与遗漏、总时间及总成本。比较保证能力，则应核对完成了什么命题及其信任前提。把发现效率与排除证据分别评价，才能同时保留这项工作的实际进展和它尚未解决的问题。

@@opinion-end@@
