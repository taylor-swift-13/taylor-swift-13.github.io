形式化验证

Compiler in the Loop 任务的消亡：方法增益会被模型迭代吞噬吗？从 Vero 到 CoCo-Prover 再到 Prove2Me

从仓库级证明、成本调度到费马大定理形式化，分析模型能力与证明基础设施各自解决的问题。

一、从三篇论文说起

1.1 Vero：仓库级的可验证代码生成

Ye 等人的 Vero: Can AI Agents Build Formally Verified Software Repositories? 于 2026 年 8 月 13 日发布 arXiv 版本（arXiv:2608.13522）。它问的是：AI 代理能否为一个多模块代码仓库同时写出实现和机器可检查的证明？此前的基准大多只考单个函数，或者给定实现后让代理补证明。仓库里的模块会共享类型、调用彼此的 API，局部证明成功并不意味着整个项目都能通过验证。

Vero 收集了 43 个来自真实仓库的多模块 Lean 4 实例，来源包括 Python、Dafny、Verus 和 Coq。每道题都有固定 API、人工整理的形式规格和参考实现。代理可以只给参考实现补证明（proof-only），也可以自己写实现和证明（code-and-proof）。如果发现题目有错，还可以提交证明，指出规格无解或参考实现违反规格。配备 Lean 工具链的最强编码代理完整解决了 27/43 个实例。

1.2 CoCo-Prover：先证什么，花多少钱

Yao 等人的 Cost-Efficient Theorem Proving via Agent Orchestration in Program Verification 被 NeurIPS 2026 Workshop on AI for Verifiable Coding（VERICODEGEN）接收为海报论文，arXiv 版本于 2026 年 10 月 7 日发布（arXiv:2610.09681）。论文除了看证明成功率，还算模型调用的费用。一个程序可能有数百条互相依赖的证明义务；按什么顺序证明、哪些引理值得先做，都会影响最后的账单。

CoCo-Prover 用一张图记录单条证明的拆解过程，另一张图记录定理与引理的依赖，再据此选择下一个目标、调用的代理和预算。它在 五个 Lean 4 基准上的完成率均为最高或并列最高，其中两个达到 100%；与实验中最强的基线相比，模型费用最多降低 30.9%。这些成绩是在什么模型配置下取得的，是后文要细看的问题。

1.3 Prove2Me：多人、多代理怎样一起写证明

Chen 等人的 Prove2Me: An Open Collaborative Platform for Scaling Math Formalization 于 2026 年 8 月发布，8 月 31 日更新到 v2。它关心的是大规模形式化项目的协作：用户发起一项 mission，多个 AI 代理分别贡献证明，平台负责检查提交、记录依赖，并让后来者找到已经证明的结果。Lean 4 负责检查每份证明；代理之间怎样分工、怎样复用成果，则由平台安排。

9 月，Anthropic 公布了使用 Prove2Me 完成费马大定理形式化的项目报告，第五节会结合这次运行讨论平台的作用。

二、Vero：一个函数证完了，仓库还没证完

图 1：题目怎样制作、评分和纠错

1A—1C：先把真实仓库做成 Lean 题目

**1A：选取源项目。**其中 13 个项目来自 Dafny、Verus、Coq 等形式化语言，需要翻译已有定义和规格；另外 30 个来自 Python，已有可执行代码，但要根据代码、文档和测试补写规格。转换后仍保留多模块结构，各 API 继续共享类型、辅助定义和不变量。

1B：制作 Lean 项目。Discover 列出原仓库的声明；Select + Plan 选择要保留的声明，安排模块和依赖，确定 Lean 接口；Translate 按依赖顺序转换定义和实现。Python 项目还要经过 Spec Write：先用自然语言写性质，经人工核对后再转成 Lean 命题。最后由 Validate 检查构建、项目结构，以及规格与原项目语义是否一致。每一阶段都要经过人工审核，图中的 human-gated 就是这个意思。

**1C：得到一道题。**每个 Lean 仓库包含数据类型与辅助定义、API 签名 A\mathcal AA、形式规格 S\mathcal SS 和参考实现。43 个仓库共有 743 个计分 API、2,705 条计分规格。规格写的是实现应满足的命题；参考实现供 proof-only 模式使用，也要接受后续审计。

2A—2B：同一套规格考两种不同工作

2A proof-only 固定参考实现，代理证明全部 Si(canonical)S_i(\texttt{canonical})Si​(canonical)。2B code-and-proof 只固定 API 签名和规格，代理自己实现 API，再证明同一组规格。后一种模式多了一项选择：同样正确的算法，换一种数据表示，证明难度可能差很多。两种模式最后都按整个仓库评分，全部规格通过才算完成。

3A—3B：判分之外，还要修正题目本身

**3A：独立评分。**评分器从一份未修改的 Lean 项目开始，只放入代理允许提交的内容：proof-only 放证明，code-and-proof 放实现和证明。接口、辅助定义、规格，以及 proof-only 的参考实现都保持固定。随后 Lean 检查全部证明；评分器还检查公理白名单，筛查可能改变证明目标含义的特殊声明。所有规格都通过，才算解决这个仓库。

**3B：检查题目有没有错。**代理可以另交一份 Lean 证明，指出参考实现违反规格、某条规格无解，或多条规格无法同时满足。Base64 案例属于最后一种：同一个分类函数遇到填充字符 =，一条规格要求返回 some none，另一条要求返回 none。两个返回值不同，函数不可能同时满足这两条要求。

基准实例究竟给了什么

每道 Vero 题都是一个多模块 Lean 4 项目。制作人员固定数据类型、辅助定义、API 签名和规格，代理填写实现与证明。论文用下面的记号表示接口和规格：

A={a1,…,am},S={S1,…,Sn},Si:RepoImpl→Prop. \mathcal A=\{a_1,\ldots,a_m\},\qquad \mathcal S=\{S_1,\ldots,S_n\},\qquad S_i:\texttt{RepoImpl}\to\mathtt{Prop}. A={a1​,…,am​},S={S1​,…,Sn​},Si​:RepoImpl→Prop.

RepoImpl 的每个字段对应一个 API。canonical : RepoImpl 是本次要证明的具体实现：proof-only 使用参考实现，code-and-proof 使用代理实现。规格 SiS_iSi​ 以实现为参数，所以同一条规格可以用于检查不同的实现。

这里分开了三件事：RepoImpl 规定接口形状，SiS_iSi​ 规定一个实现应满足什么，canonical 指定本轮实际检查哪个实现。规格调用 impl 的字段，不能直接绑定到参考代码，否则换成代理实现后，证明可能仍在检查参考代码。以实现为参数还让审计能区分“这个实现违反规格”与“根本不存在满足规格的实现”，两者的量词不同。这个设计见原论文 §3.1。

以论文图 2 的银行账户为例，接口和规格可以简写为：

structure RepoImpl where
  createAccount : AccountId → Ledger → Ledger
  accountExists : AccountId → Ledger → Bool
  getBalance : AccountId → Ledger → Option Balance

def canonical : RepoImpl := {
  createAccount := Bank.createAccount,
  accountExists := Bank.accountExists,
  getBalance := Bank.getBalance
}

def spec_create_zero_balance (impl : RepoImpl) : Prop :=
  ∀ (id : AccountId) (ledger : Ledger),
    impl.accountExists id ledger = false →
    impl.getBalance id (impl.createAccount id ledger) = some 0

theorem proof_create_zero_balance :
    spec_create_zero_balance canonical := by
  sorry

这条规格调用 impl 的三个 API：如果账户原本不存在，创建后查询余额应得到 some 0。canonical 指定这些 API 的具体函数。证明 spec_create_zero_balance canonical，就要用这些函数的定义，对所有账户和账本证明该性质。上面的代码据论文图 2 整理。

两种模式的证明目标都是

∀Si∈S,Si(canonical). \forall S_i\in\mathcal S,\quad S_i(\texttt{canonical}). ∀Si​∈S,Si​(canonical).

proof-only 固定参考实现，code-and-proof 则先由代理填写每个 ai∈Aa_i\in\mathcal Aai​∈A 的函数体。无论选哪种实现，都得证明完同一组规格。按仓库评分也因此有必要：即使容易的性质都证完了，只要还剩一条关键规格，任务就没有完成。

从代理的工作目录到独立评分

Vero 的方法包括题目格式、制作、评分和审计；答题时使用的是配备 Lean 工具链的编码代理，论文没有为它规定一套专门的引理分解算法。代理可以编辑文件、构建项目和尝试证明，但评分器只接收 !benchmark 标记之间的内容，再把这些内容填回一份未修改的题目副本。代理即使在工作目录里降低了规格要求、修改了固定辅助定义，评分时也会恢复原题。

构建通过后，评分器用 #print axioms 检查每条计分定理的实际依赖。默认允许 Classical.choice、propext、Quot.sound；个别实例的额外可信公理由 manifest.trusted_axioms 记录。依赖 sorryAx 的结果算未填完，依赖其他非白名单公理的结果也不计通过。因此，“文件能编译”只是其中一关。

最后还要检查新声明是否改变了规格的实际含义，或使逻辑上的函数与运行时函数脱离。附录 D 举了两种情况：用忽略参数、恒为真的比较关系替代正常类型类实例，让比较规格变得空洞；用不可计算的规格见证定义逻辑函数，再通过 @[implemented_by] 指定另一份运行时代码，使证明检查的函数与执行的函数不同。评分器结合规则筛查和 LLM 判断，并在代理可编辑的实现文件中直接拒绝 @[implemented_by]。三层检查的具体规定见附录 D。

题目也会错：三个审计案例

Vero 的项目涉及密码协议、分布式系统、数据结构等领域。跨语言翻译可能改变规格的含义；从 Python 代码补写规格也可能漏掉前提。人工审核之后，仍有必要检查参考实现是否满足规格，以及规格本身能否成立。

三类错误分别对应下面的命题，代理发现问题时需要给出它们的证明：

¬⋀S∈SS(canonical)参考实现违反规格；¬∃ impl:RepoImpl, S(impl)某条规格无解；(∀S∈S′, ∃ impl, S(impl))∧¬∃ impl,⋀S∈S′S(impl)各条规格单独可满足，却无法同时满足。 \begin{aligned} &\neg\bigwedge_{S\in\mathcal S}S(\texttt{canonical}) &&\text{参考实现违反规格；}\\ &\neg\exists\,impl:\texttt{RepoImpl},\ S(impl) &&\text{某条规格无解；}\\ &\bigl(\forall S\in\mathcal S',\ \exists\,impl,\ S(impl)\bigr) \land\neg\exists\,impl,\bigwedge_{S\in\mathcal S'}S(impl) &&\text{各条规格单独可满足，却无法同时满足。} \end{aligned} ​¬S∈S⋀​S(canonical)¬∃impl:RepoImpl, S(impl)(∀S∈S′, ∃impl, S(impl))∧¬∃impl,S∈S′⋀​S(impl)​​参考实现违反规格；某条规格无解；各条规格单独可满足，却无法同时满足。​

三类审计提交的证明对象不同。第一类只需证明固定参考实现至少违反一条规格，不能由此断定题目无解。第二类需要对任意 impl : RepoImpl 证明某条规格不能成立，换算法也解决不了。第三类除了证明一组规格无法同时满足，还要分别给出每条规格可满足的证据；否则其中某条本来就无解，应归入第二类。审计是独立的负面证据路径，交回制作人员检查和修题，并不允许代理直接删掉原任务中的要求。这个区分见原论文 §3.5。

附录 F 的 verdict 案例涉及 Base64 字符分类函数 charToBits。第一条规格处理填充字符，第二条规定应拒绝哪些字符：

def spec_char_to_bits_padding (impl : RepoImpl) : Prop :=
  impl.verdict.charToBits 0x3D = some none

def spec_char_to_bits_reject (impl : RepoImpl) : Prop :=
  ∀ (c : UInt8),
    (c < 0x2B ∨ (c > 0x2B ∧ c < 0x2F) ∨
      (c > 0x39 ∧ c < 0x41) ∨
      (c > 0x5A ∧ c < 0x61) ∨ c > 0x7A) →
    impl.verdict.charToBits c = none

= 的字符值为 0x3D。第一条要求 charToBits 0x3D = some none，把它识别为填充字符。但 0x3D 也落在第二条的拒绝区间 c > 0x39 ∧ c < 0x41 中，因此第二条要求同一次调用返回 none。GPT-5.5（xhigh）据此提交了 Lean 可检查的联合不可满足证明。矛盾很具体：拒绝区间把本应允许的填充字符也包含进去了。

修复时只需在拒绝条件的第三段排除 0x3D：

(c > 0x39 ∧ c < 0x41 ∧ c ≠ 0x3D)

改后，= 仍被识别为填充字符，第二条规格不再要求拒绝它。原来的矛盾曾通过人工审核和 Lean 类型检查：命题写得合法，不等于命题能成立。论文报告，审计在 43 个实例中定位并修复了 38 条有缺陷的规格，涉及 9 个实例，另有 6 组联合不可满足的规格。

另外两类错误也见于附录 F。verified_ironkv 有三条规格没有约束比较器 KeyTrait 的行为。GPT-5.5（xhigh）构造了一个总是返回 Ordering.Less 的比较器：含两个相同 Unit 元素的列表因此满足“有序”的前提，却仍有重复元素，相关规格对任何实现都无法成立。作者加入 LawfulKeyTrait，要求比较结果中的“相等”与元素相等一致，再修复这三条规格。

verified_bitmasks 的问题出在参考实现与规格不符。三条规格要求位运算保持第一个输入的位数，却没有要求两个输入等长。实现用的是 zipWith，结果长度取两个输入长度的较小值；第二个输入更短，规格就会失败。修复需要加上输入等长的前提。另有四条规格在位数超过 64 位机器字的表示范围时失败，需要补上范围限制。作者随后为这七条规格逐一编译了参考实现的正向证明，确认修复后的要求能够满足。

这些审计证明给了制作人员明确的修改依据：到底是实现错了、前提漏了，还是两条要求互相矛盾，都能在 Lean 中指出来。

为什么局部通过率很高，完整仓库仍难完成

Vero 原论文给每个仓库 90 分钟，评测四种编码代理配置的两种任务模式。图 3 中，GPT-5.5 xhigh 在 code-and-proof / proof-only 下分别完成 27/43、25/43；GPT-5.5 medium 为 2/43、6/43；Opus 4.8 为 8/43、10/43；Sonnet 5 两种模式均为 2/43。

GPT-5.5 xhigh 的逐规格通过率分别为 87.3% 和 85.8%，完整仓库却只完成了 27 和 25 个。还有一个差距不能忽略：同一个 GPT-5.5，proof-only 从 medium 的 6/43 提升到 xhigh 的 25/43。后面判断 CoCo-Prover 的效果时，必须把这个强配置算进去。

原论文图 3。曲线统计 90 分钟内累计完整解决的仓库；右侧展示不同配置解决了哪些实例。

涉及全局覆盖性的规格失败率最高，为 47.1%。同一仓库中，使用给定辅助定义的规格失败率高出 14.9 个百分点，重复调用同一 API 的规格高出 11.7 个百分点。难题往往要求证明多次执行后仍保持某个不变量，也更依赖辅助引理。

附录 H 的 deposit_sc 来自 ConsenSys 的 Dafny Merkle 树增量提交合约，含 79 条规格，分布在 Bits、Tree、Merkle、Contract 四个模块。GPT-5.5（xhigh）在两种模式下都证明了全部规格。code-and-proof 的四个证明模块共 6,052 行非空代码，含 99 条代理编写的辅助定理。证明从位列表计算和树结构开始，逐步做到 Merkle 根计算，再做到合约状态更新。辅助定理占证明文字的 54.3%；规格证明的中位长度为 9 行，辅助定理为 19 行。

spec_incremental_equals_batch 要求一批 deposit 的折叠结果与逐次 deposit 一致。直接对批次归纳还不够：每一步都需要中间状态有效、values 追加了已处理的输入，以及树高、合并函数、默认值保持不变。代理把这五项要求合成一条更强的辅助命题，再做归纳。上层规格随后调用该引理即可。类似地，prove_same_leaves_same_root 的正文只有两行，背后却用到一条 94 行的树归纳引理。

较早一轮评估中，这个实例还剩 7/79 条规格未证。它们都依赖一条边界引理，描述叶子数组增加一个元素后 Merkle 路径的兄弟节点怎样移动，合约的主要有效性不变量也在其中。本轮评估中，同一 GPT-5.5（xhigh）配置补上了这条引理，完成全部 79 条规格。可见，强通用代理已经能自己搭建大型引理库。专门的调度方法还值多少，要与这样的代理比较。

三、CoCo-Prover：怎样安排证明，怎样少花钱

CoCo-Prover 每轮决定先证明哪些目标，再决定调用哪类代理、给多少预算。它按实际模型费用记账，分别统计输入、缓存和输出 token。

两张图：定理之间的依赖，定理内部的步骤

两张图在论文中记为：

D=(L,ED),Hℓ=(Aℓ,Oℓ,Eℓ)(ℓ∈L). \mathcal D=(L,E_{\mathcal D}),\qquad \mathcal H_{\ell}=(A_{\ell},O_{\ell},E_{\ell})\quad(\ell\in L). D=(L,ED​),Hℓ​=(Aℓ​,Oℓ​,Eℓ​)(ℓ∈L).

声明依赖图 D\mathcal DD 记录目标定理和辅助引理；边 u→vu\to vu→v 表示 vvv 当前的证明或计划使用了 uuu。因此，图中有一条依赖边，并不意味着辅助引理已经证明，也不意味着上层证明已经接上。引理会被标为稳定、暂定或废弃。每条定理内部另有一张AND/OR 证明超图 Hℓ\mathcal H_{\ell}Hℓ​：AND 节点 AℓA_{\ell}Aℓ​ 记录 Lean 目标状态，OR 节点 OℓO_{\ell}Oℓ​ 记录候选证明步骤；选择一个步骤后，它产生的全部子目标都要完成。EℓE_{\ell}Eℓ​ 保存 Lean 已检查的转换。前一张图用于复用引理，后一张用于记录当前定理证到了哪里。

案例一：一个字符串定理为什么要九条引理

附录 D.1 的 CLEVER prob_15 要求实现 string_sequence，将 0 到 n 的十进制表示用空格连接。代码是 " ".intercalate ((List.range (n+1)).map Nat.repr)，规格却用 splitOn " " 解析输出，要求段数为 n+1，第 iii 段等于 i.repr。证明得先说明数字表示中没有空格，再说明拼接后切分能还原原列表，还要接上 Lean 字符串库底层的 UTF-8 字节扫描和私有累加器。库中有列表级的 List.splitOn_intercalate，但没有能直接用于这里的字符串定理。

CoCo-Prover 为此提出九条辅助引理。implementation_splitOn 连接规格与实现，nat_repr_toList_no_space 排除数字中的空格，string_splitOn_space_intercalate 处理字符串拼接和切分；其余引理逐步接上字符列表、私有累加器、String.splitOnAux 和 UTF-8 偏移量。图 6 给出了依赖关系。整次运行有 8 轮控制循环、18 次路由调用：7 次规划，11 次写证明；规划调用使用 high-thinking，证明脚本调用使用 low-thinking。九条引理各提出、证明一次，没有回滚，也没有废弃引理。

案例二：56 条区间规格怎样复用引理

附录 D.2 的 Vero prob_14 是一个半开整数区间 [lo,hi)[lo,hi)[lo,hi) 的集合库。区间列表表示各区间覆盖的整数，covered x ivs 判断 xxx 是否在其中。overlaps、mergeOverlaps、chop 三组操作分别有 6、39、11 条规格，共 56 条，要求合并保持覆盖、结果严格有序且不重叠、同一覆盖集合有唯一规范形式、排列输入不改变结果，以及切除区间与再次合并满足相应关系。

难点藏在 mergeOverlaps 内部。它先用 insertByLo/sortByLo 排序，再用 coalesce 合并；插入是结构递归，排序用折叠，合并则在修改列表头后做良基递归。直接展开定义会让目标迅速变大。论文中的 prove_merge_coverage 先用插入、排序的覆盖引理，再用 coalesce_coverage_of_pairwise_lo；prove_merge_disjoint_strict 则需要排序输出非空、按左端点有序，以及 coalesce_disjointSortedNonempty。证明 coalesce 保持覆盖时，要用函数自己的归纳原则 coalesce.induct，并将点 xxx 和有序性前提一起放进归纳目标，才能在合并后的递归调用中使用归纳假设。有了覆盖不变和规范形式，上层的唯一性、排列不变性才容易证明。

规划器也会提出错误引理。它最初猜测 insertByLo iv ys 的输出区间都非空，但取 iv = [0,0)、ys = [[0,0)] 就能反驳：iv 为空时函数原样返回 ys，输出仍含空区间。系统在证明前发现这个反例。规划器补上“ys 中每个区间都非空”的前提，证明后进一步得到 sortByLo_output_nonempty；后来 28 条目标间接依赖这条引理。

整次运行有 34 轮控制循环、175 次路由调用，完成 56/56 条目标，费用约 $19。最终文件有 2,471 行证明、55 条实际使用的辅助引理，依赖链最深 6 层。8 条目标由确定性自动化完成，2 条由模型直接证明，其余 46 条使用了辅助引理或已证目标。sortByLo_pairwise_lo 和 sortByLo_output_nonempty 分别被 31、28 条目标间接依赖。过程中有 52 次有理由的回滚，例如自动化过早展开递归定义后，退回安全节点，改用归纳或已有引理。同一 Terra 模型的编码代理基线只完成 5/56。

随着证明推进，已证目标也像辅助引理一样被后续目标调用。56 条规格因此共用一套证明库。

5/56 与 56/56 的差距说明，这种安排对 Terra 处理该题很有帮助。但强模型在同一题上能做到什么，论文还没有测量；Vero 的 deposit_sc 已经展示了强代理自行建立大型引理库的能力。

五、Prove2Me：费马项目为什么需要一个协作平台

5.1 把定理和证明分开提交

Prove2Me 将一个形式化项目称为 mission，包含主目标、所需定义和沿证明路线排列的里程碑。每条定理是一张独立卡片，写明自然语言描述、Lean 陈述和编译环境；按论文的提交格式，陈述以 := by sorry 结尾。证明另用一份文件提交，其中 solution 必须与目标类型完全相同，且不含 sorry 或新增公理。不同代理因此可以对同一陈述分别提交证明。

这些提交在固定的 Lean / Mathlib 环境中检查。若陈述有误，代理也可以提交它的否定证明。具体规则见平台论文第 3 节。

定理卡片分为自然语言描述、preamble 和形式陈述。preamble 列出 Mathlib 及平台定义文件的导入；环境固定工具链与 Mathlib 版本，不同环境相互隔离。提交陈述时编译成功，只说明这份声明在所选环境中成立为一个合法的待证任务，还没有得到证明。提交证明时，平台在相同环境中编译，再比对 solution 与目标的类型；证明文件还须附自然语言说明。若提交否定证明，solution 的类型则是原目标的否定。输入、环境和检查条件见原论文 §3.1–3.2。

5.2 先搭证明框架，再分头证明子定理

Prove2Me 的 proof-sketch 允许先导入尚未完成的子定理 L1,…,LkL_1,\ldots,L_kL1​,…,Lk​，写出不含 sorry 的上层推导。论文的 Property 1 说明：等这些子定理全部得到验证，上层定理也就得到验证。因此可以先证明“这些子定理足以推出主目标”，再把子定理分给不同代理。每个子定理最后仍要有 Lean 证明。

这里的 sketch 仍是一份 Lean 证明代码。若目标是 AAA，导入待证的 BBB、CCC，提交者要在自己的证明体中写完使用它们推出 AAA 的步骤。用逻辑记号说，当前建立的是 B,C⊢AB,C\vdash AB,C⊢A；尚未建立的是 ⊢B\vdash B⊢B 和 ⊢C\vdash C⊢C。这就是分解中的连接部分。本文用这个记号解释其作用，平台并不要求另建一个名为 bridge 的对象。

“不含 sorry”在这里指 sketch 自己的证明体；导入的开放定理仍可能以 sorry 结尾。因此，sketch 被接受时建立的是条件关系，不能直接称为完整的无占位符证明。等所有导入子定理都得到验证，再沿依赖关系递归检查到已完成的叶子，上层目标才算验证。代理证明一个子定理只需该子定理及其环境，不必下载或编译它的父目标。这个条件保证和局部提交方式见原论文 §4.2、Property 1。

陈述与 proof-sketch 提交后不再修改，代理可以并行处理各自的子定理。证明完成后，所有依赖它的目标都可复用；若子定理被否证，则要重写依赖它的证明路线。平台保存这张依赖图，代理不必各自在上下文里记住整个项目的进度。

不可变性保证各代理始终针对同一份陈述工作。若某个子定理漏了前提，不能直接修改旧陈述，让已经接受的上层连接悄悄改变含义；需要提出修正后的声明和新的 proof-sketch。原论文 §4.5 的实例中，一个代理否证了 gotsman_linial，另一个代理随后提出补上边界条件的 gotsman_linial_with_zero，用修正后的形式化完成该分支。

论文以黄浩的敏感度猜想为例。证明需要 Cauchy 特征值交错定理、递归矩阵 AnA_nAn​ 的谱，以及由矩阵特征值得到图最大度的界。矩阵定义为：

A1=[0110],An=[An−1II−An−1]; A_1=\begin{bmatrix}0&1\\1&0\end{bmatrix},\qquad A_n=\begin{bmatrix}A_{n-1}&I\\I&-A_{n-1}\end{bmatrix}; A1​=[01​10​],An​=[An−1​I​I−An−1​​];

谱引理要证明特征值为 n\sqrt nn​ 和 −n-\sqrt n−n​，各有重数 2n−12^{n-1}2n−1。上层 proof-sketch 导入所需定理，证明它们能推出敏感度结论。图 5 中，椭圆表示定理或定义，紫色方块表示连接它们的 proof-sketch；同一条已证引理可以用于多条路线。

5.3 编译、找引理和核对陈述

**编译。**数十个代理共同修改一套 Lean 文件，容易发生文件冲突，依赖的定义或引理变化还会引起大量重编译。Prove2Me 将陈述和证明拆开，代理在独立环境中证明子定理，不必下载并重编译整个上层工程；服务端检查提交，再更新依赖图。模型的局部证明能力再强，也仍需要处理这些构建和协作问题。

**里程碑。**仅有依赖图还不够：不同代理可能把同一个数学结论写成参数、定义或前提不一致的 Lean 声明，彼此无法直接调用。mission 的 captain 为关键里程碑提供权威的自然语言陈述，并确认其对应的标准形式化。代理从里程碑列表进入项目，针对同一陈述工作，遇到已证结果直接复用。完成条件也不只是“里程碑全证完”，还要有 proof-sketch 将它们接到主目标。共享目标怎样固定，见原论文 §4.4。

**检索。**每张定理卡片都有自然语言描述。代理创建新定理前先搜索，找到适用结果便直接导入。已验证的成果存入 Formalpedia，其他证明路线或 mission 也可复用，减少重复形式化。

**审计。**Lean 检查证明能否推出形式陈述，但陈述有没有表达原来的数学意思，还需要核对。Prove2Me 要求人审核 mission 的主目标、定义和里程碑，允许代理自行补充中间引理。平台另让独立代理读取 Lean 声明，将其回译成普通数学描述，再由人对照原文。图 3 展示了这种 read-back：量词范围、空乘积和边界条件都会被写出来，便于发现仅看定理名称察觉不到的偏差。

审核也有明确的提交顺序。captain 的代理先起草私有 mission 提案，草稿此时可改；人逐条确认核心陈述后，平台编译并发布不可变定理，再由 moderator 审查 mission。read-back 代理只看 Lean 声明及依赖定义，不看原始来源，由人比较回译结果和原文。中间引理无需逐条接受同样的语义审核：最终信任的是已审核目标的完整 Lean 证明，而不是代理挑选的分解本身。该范围见原论文 §3.3。

5.5 费马大定理项目的运行与复核

据 Anthropic 9 月的项目报告，Claude 代理最初已经能完成一些局部任务，但工作越积越多，各代理逐渐无法掌握共同进度，协作和复用出现问题。早期尝试贡献了约 7% 的非样板代码行。切换到 Prove2Me 后，代理通过依赖图查看未完成目标，独立编译减少构建负担，自然语言检索帮助寻找已有引理。团队随后使用 Claude Code 多代理环境和一个内部研究模型，在 11 天内完成端到端形式化，消耗约 60 亿输出 token，写出约 1,300 万行 Lean。最终证明用了约 29,500 条中间定理；公开仓库列出 29,511 条定理、60,475 个模块。

最终目标在公开仓库中写为：

theorem fermat_last_theorem (n : ℕ) (hn : 3 ≤ n)
    (a b c : ℕ) (ha : 0 < a) (hb : 0 < b) (hc : 0 < c) :
    a ^ n + b ^ n ≠ c ^ n

FinalCheck.lean 要求该定理只依赖 propext、Classical.choice、Quot.sound 三项 Lean 标准公理，并由它推出 Mathlib 的费马大定理陈述。报告还列出复核过程：重新编译全仓库，用 comparator 比对最终陈述与 Mathlib 定义，再用第二个内核 nanoda 检查导出的声明。Kevin Buzzard 也重新编译并运行了 comparator。这些检查覆盖最终陈述和它所依赖的证明。

证明采用 Frey–Serre–Ribet–Wiles–Taylor–Wiles 路线，复用了 Mathlib，以及先前 FLT 和正则素数项目的部分成果。新写的大规模主体处理高指数情形，再接上已有的小指数结果。Buzzard 在重新编译后也指出，代码量大、编译昂贵；便于人阅读、适合长期收入 Mathlib 的形式化工作仍在继续。

报告中的路线图分为 Mazur 的不可约性、Ribet 的降层、Wiles 的模性三条分支，最后汇合到 Frey 曲线不存在，再推出费马结论。每个框下都标有具体的 Lean 定理或定义，代理可以沿依赖关系查看进度和领取目标。

5.6 这个项目说明了什么

费马项目中，代理接入平台前就能证明部分结果，卡住的是共同进度、协作和复用。Prove2Me 提供的依赖图、独立编译和自然语言检索正好处理了这些问题。它让代理知道还有哪些目标没做，避免反复编译整个工程，也更容易找到已证引理。

接入平台后完成证明，是平台在这次项目中发挥作用的证据。不过，这份报告并非控制变量实验，不能仅凭前后结果算出平台的独立增益。较稳妥的判断是：局部证明能力已经很强时，大项目仍需要让这些证明能够衔接、检查和复用的协作工具。

六、Compiler in the Loop 的方法增益还能保留多少

6.1 模型越强，方法越宏观；模型越弱，方法越细节

写 Lean、看报错、修改、再编译，是 compiler in the loop 最基本的循环。模型变强后，同样的循环可能少试几次就成功。若一个方法的贡献只是帮助模型修补局部证明，那么更新模型之后，还能省多少调用、提高多少成功率，就需要重新测量。CoCo-Prover 在所测模型上取得了改善，但它尚未超过 Vero 的强基线，也缺少更强模型和更高思考强度下的对照。

本文的判断是：**模型越弱，方法越需要介入细节；模型越强，方法的价值越往宏观移动。模型会逐渐吞噬具体方法。**能力不足时，系统要替模型选择 tactic、保存每一步状态、规定何时回溯；能力变强后，这些决策越来越多地由代理自己完成。原先值得单独设计的流程，可能变成一次普通工具调用中的行为。

这并不只意味着“更强的模型少试几次”。更深的变化是，方法与模型之间的分工发生了移动。弱模型只能提出一个候选步骤，外部程序就得组织候选、验证结果、展开子目标并决定回溯。强模型能在一次代理运行里完成这一串工作，原先写在调度器里的决策便进入了模型的行为。研究者仍然可以给这些行为命名，但命名本身已经不能说明方法有额外增益。

对强模型代理，我倾向于不再把 tactic 级别的选择和回溯当作需要刻意教授的核心能力。给它 Lean 环境、编译反馈和足够预算，它通常已经会尝试策略、根据子目标调整证明，失败后撤回重试。例如，simp 没有关闭目标，它会检查剩余条件，换用现有引理或补一条 have；一段代码无法编译，它会修改代码，再运行验证器。这些行为发生在代理的实际尝试中，不必先由外部控制器逐条指定。

因此，CoCo-Prover 的内部 AND/OR 超图需要回答一个更具体的问题：当强代理已经会选择 tactic、产生子目标和回退时，把这些操作再显式记成图，究竟增加了什么？如果收益来自恢复进度、保留已验证片段或减少上下文重传，就应当直接测这些收益。仅仅把代理本来会做的事表示成一张图，还不足以说明它改善了证明。前文提到的内部超图独立消融，正是为了区分行为能力与状态保存的贡献。

模型吞噬方法，也不是说方法从此没有意义。一种外部方法可以先帮助弱模型完成任务，其轨迹随后进入训练，让后来的模型学会同样的行为。方法曾经有用，但它的推理时收益可能随着训练和模型迭代下降。只在较弱模型上取得提升，不能保证它在下一代强模型上仍值得保留。

6.2 refine、decompose、search 也正在被代理内化

方法上移到宏观之后，还会遇到同样的问题。refine、decompose、search 曾经可以作为三个显式模块：一个负责修正，一个负责分解，一个负责尝试不同路线。如今，对具备这些能力的强代理，prompt 不必每次提醒“失败后修正”“必要时分解”“多试几次”；它会自己基于验证器报错修改证明，把大问题拆成小问题，对同一目标进行多次尝试。把三个行为分别写进 prompt，再交给三个代理，不自动构成三项新增能力。

refine 是其中最清楚的一项。目标类型与当前项不匹配，就检查参数、隐式变量和等式方向；缺少某个前提，就寻找能提供该前提的引理；还有未完成目标，就继续补证明。这里的下一步可以由验证器反馈直接驱动。Goedel-Prover-V2已经把 Lean 验证器指导的自我修正纳入训练流程，并结合逐渐变难的合成任务、专家迭代和强化学习。修正经验因此可以进入模型，而不必一直作为外部修补模块存在。

decompose 也有相同趋势。代理发现主目标太难，会提取一个局部性质作为辅助引理，先证明它，再尝试接回主目标。DeepSeek-Prover-V2先用 DeepSeek-V3 递归分解问题，把已解决子目标的证明与自然语言推理组合成强化学习的冷启动数据。这项工作展示了分解经验怎样进入模型训练。它的数据生成阶段仍使用分解提示，但提示产生的经验可以被后续模型学走。

但会提出辅助引理，不等于提出了正确的分解。若主目标是 AAA，代理给出 BBB、CCC，它还得证明 B,C⊢AB,C\vdash AB,C⊢A，并保证 BBB、CCC 本身可证。没有这个连接，代理可能在解决越来越多的小问题，却始终接不回原目标。前文 CoCo-Prover 与 Prove2Me 的区别，也应当放在这里看：分解想法可以由模型提出，系统仍要保存并检查分解的实际依赖和完成条件。

search 则表现为：一条路线走不通，就换一个引理、另一种归纳方式或不同的数学表示，再尝试一次。强代理通常已经会这样工作，外部系统不必每次告诉它“还有另一条路”。不过，知道要多试几次，与有效分配预算仍有距离。系统是否避免重复路线、是否在合适的时候停止、是否把失败经验交给后续尝试，才是值得检验的额外贡献。

三者之中，我认为 refine 是目前做得最好的一项。它的反馈最直接：修改前有具体报错，修改后能立即验证。decompose 的好坏可能要等若干子引理完成后才能判断，search 的路线选择也常常缺少即时反馈。这个排序是本文的判断，并非统一实验的结论；但它解释了为什么只围绕报错设计一套修补流程，最容易被更强模型替代。

A Minimal Agent for Automated Theorem Proving（AxProverBase）提供了一个有用的参照：它只保留迭代修正、库检索和上下文管理，就能以简单架构取得有竞争力的结果，并发现迭代方式在采样效率和成本上优于多次单次生成。它没有证明完全不需要提示，而是提醒我们，比较复杂方法时，基线也应当是一个能运行、能读反馈、能继续尝试的代理。

宏观编排仍然可能有实测收益。Goedel-Architect生成定义与引理的依赖图，并行证明节点，再根据失败诊断和否证修改全局图，同时保留已经证明的节点。作者在同一模型下的比较显示，这种编排仍优于直接生成和工具代理基线。它的贡献因此不能只概括成“让模型分解”：它还组织了跨引理的反馈，保存成果，并修订整条路线。这些具体机制才是方法继续存在的理由。

6.3 最值得外置的是记忆：让重要上下文持续存在

在这样的趋势下，我更看好 **external memory：把重要上下文持久化到模型之外，让后续运行和多个代理共同使用。**一个代理会自己修正证明，不等于它在换上下文后还记得先前找到了什么；一个代理会拆问题，也不等于其他代理知道这份拆解、使用相同的定义，或者能复用已经完成的部分。模型能力越强，重新做这些工作的浪费反而越明显。

这里有一个根本区别：修正、分解和尝试路线，可以是代理当下的推理行为；项目记忆则要跨越这次推理的边界。模型参数可以保存通用证明经验，却不会自动保存某个正在进行的项目昨天新证明了哪条引理、谁改了哪个定义、哪个反例否定了一条路线。这些信息必须在运行过程中写下来，并允许其他代理读取。

例如，代理甲为主目标 AAA 提出 BBB、CCC，写出了条件证明 B,C⊢AB,C\vdash AB,C⊢A，随后证完了 BBB。如果这些信息只留在甲的上下文中，代理乙接手时可能重新分解 AAA，再次证明 BBB，甚至使用另一份不兼容的 CCC。共享记忆应当让乙直接看到：主目标和条件连接的准确版本、BBB 的已验证证明、CCC 的待证状态，以及甲在 CCC 上已经失败的尝试。乙的任务就明确地变成继续证明 CCC，或者用新路线替换这份分解。

这种记忆不要求把所有聊天原样堆进去。更有用的是把会影响后续工作的结果保存为可检索对象，并附上证据：代码位置、编译结果、依赖和失败原因。长记录可以留作追溯，下一位代理首先需要的是当前可信状态。否则，虽然信息持久化了，代理仍得花大量上下文重建项目进度。

LeanAgent从持续学习的角度处理知识积累：用动态数学知识数据库管理不断扩展的 Lean 知识，结合难度课程和渐进训练，让检索与证明跨仓库持续改进。它并非多代理共享记忆实验，但说明了持久知识库与检索可以成为独立的系统组成部分。Prove2Me 则更直接地处理多个代理围绕同一项目工作的状态共享。 需要保存的内容应当能直接支持下一次工作：定理的准确陈述和环境版本、已经通过验证的证明、仍待完成的条件依赖、可复用引理的位置，以及失败路线和失败原因。例如，代理甲发现引理缺少非空条件，代理乙应当能读到这条结论及其反例；代理甲证完一个辅助引理，代理乙应当能直接导入它，而不是从聊天记录里猜测哪个版本可用。

这里还必须保留状态的区别：计划使用某条引理、上层条件证明已经通过、整条依赖链已经验证，是三件不同的事。CoCo-Prover 的暂定与稳定状态、Prove2Me 的开放定理与条件 proof-sketch，都在处理这一问题。共享记忆若抹平这些区别，就会把尚未完成的路线当作已证事实。

Prove2Me 在本文中的意义也因此更清楚：它把固定陈述、可检索成果、证明依赖和共同进度放到代理之外，让不同代理针对同一对象工作。其依赖与协作机制提供了一种具体实现。图在这里不仅表达“怎么分解”，还保存“大家已经完成什么、还缺什么”。这比反复提醒强代理要修正、分解和搜索，更接近大项目中持续存在的需求。

Vero 和 Prove2Me 给出了更大的任务。Vero 要求整个仓库的全部规格通过，一条关键引理没证完就不能算完成；费马项目有约三万条中间定理，除了证明单条定理，还得维护依赖、查找已有结果、安排并行工作并检查最终证明链。模型写证明的能力与项目的组织方式，都要在这样的任务上接受检验。

标题里的“消亡”说的是一种方法贡献的贬值：如果换个更强的模型就能得到同样的结果，只围绕编译报错设计修补流程，价值便会越来越小。更有希望留下来的，是跨上下文的记忆、跨代理的成果复用、固定的任务接口和最终证明链的检查。接下来的方法研究，要说明自己在这些地方解决了什么问题，也要拿当前的强模型来证明它仍然值得用。
