形式化验证中的“完成”有严格含义：实现符合事先写好的规格，且证明由 Lean 的内核检查通过。一个函数的证明可以独立搜索；一个仓库却包含多个模块、共享定义、彼此依赖的定理。某条看似局部的性质，可能需要先建立跨越几个模块的辅助引理。

[Vero: Can AI Agents Build Formally Verified Software Repositories?](https://arxiv.org/abs/2608.13522)（Ye 等，2026）提出仓库级的 Lean 4 基准；[Cost-Efficient Theorem Proving via Agent Orchestration in Program Verification](https://arxiv.org/abs/2610.09681)（Yao 等，2026）提出 CoCo-Prover，以证明图和多个代理调度证明工作。后者的案例很精彩，但本文贯穿一个更尖锐的问题：**CoCo-Prover 的优势有多少来自方法本身？如果换成更强的模型、提高思考强度，复杂调度的增益还剩多少？**

先看最容易被忽略的对照。CoCo-Prover 论文在 Vero 的 proof-only 任务上，用 GPT-5.6-Terra 完成 **23/43**；Vero 原论文的 Codex + GPT-5.5 (xhigh) 在同一基准的 proof-only 模式完成 **25/43**。CoCo-Prover 并非只测试 Terra：它还用 Gemini-3.5-Flash 完成 **26/43**，用 DeepSeek-V4-Flash 完成 **6/43**。准确的质疑是：**OpenAI 底座只测试了 Terra，未与 GPT-5.5 (xhigh) 这样的强推理配置做同条件对照。**而且 Vero 原论文每题限时 90 分钟，CoCo-Prover 对仓库任务给 8 小时、$60 上限，原始数字更不能视作公平竞赛。[Vero §4.1–4.2](https://arxiv.org/html/2608.13522v1#S4.SS1)、[CoCo-Prover §4、附录 C.1](https://arxiv.org/html/2610.09681v1#S4)

因此本文会同时做两件事：认真解释 CoCo-Prover 为什么能工作，也逐项检查其效果论证是否排除了模型能力与思考强度这两个更简单的解释。

## 一、Vero：把验证单位从函数提升到仓库

### 基准实例究竟给了什么

Vero 的一个实例是多模块 Lean 4 项目。策展者固定三类内容：数据类型和辅助定义、API 的类型签名、形式化规格。代理填入实现与证明。形式上，令接口集合为 $\mathcal A=\{a_1,\ldots,a_m\}$，规格集合为 $\mathcal S=\{S_1,\ldots,S_n\}$；`RepoImpl` 是包含所有 API 实现的结构，每个规格都具有 `RepoImpl → Prop` 类型。被验证的具体实现叫 `canonical`。这样，同一组规格既能作用于参考实现，也能作用于代理写出的实现。[论文 §3.1](https://arxiv.org/html/2608.13522v1#S3.SS1)

论文图 2 的银行例子可以浓缩为：

```lean
structure RepoImpl where
  createAccount : AccountId → Ledger → Ledger
  accountExists : AccountId → Ledger → Bool
  getBalance : AccountId → Ledger → Option Balance

def spec_create_zero_balance (impl : RepoImpl) : Prop :=
  ∀ (id : AccountId) (ledger : Ledger),
    impl.accountExists id ledger = false →
    impl.getBalance id (impl.createAccount id ledger) = some 0

theorem proof_create_zero_balance :
    spec_create_zero_balance canonical := by
  sorry
```

这里的重点不是证明语法，而是规格的**参数化**：它声明“任何满足这一性质的 `RepoImpl`，创建新账户后余额应为零”，最终证明只针对选定的 `canonical`。若把规格直接焊死在参考函数上，就无法用同一条规格同时考察代理的新实现，也难以陈述“任何实现都不可能满足它”。上面代码按论文图 2 摘取并整理，省去了具体数据类型和参考函数定义。

Vero 有两个模式。**Proof-only** 固定参考实现，代理证明每个 $S_i(\texttt{canonical})$；**code-and-proof** 让代理填入每个 API 的函数体，然后证明同一组规格对自己的实现成立。后者要求在设计实现时考虑可证明性。例如能选择更容易建立不变量的算法，但不能改变 API 类型和规格。任务以仓库为单位判定：全部规格都证明成功，才算完整解决。论文强调，单看已证明规格的比例，会被大量容易的局部性质抬高。[论文 §3.2](https://arxiv.org/html/2608.13522v1#S3.SS2)

![Vero 论文图 1：从源仓库到 Lean 基准，再到代理评测的流程](../assets/papers/vero-pipeline.png)

*原论文图 1，展示来源仓库、人工审核的翻译流水线、两种评测模式及形式化审计。来源与授权见文末。*

### 数据从何而来，以及为什么需要审计

Vero 收集 **43 个仓库实例**：13 个原本使用 Dafny、Verus、Coq 等形式化语言，需要翻译既有定义与规格；30 个来自 Python，需要把实现迁到 Lean，并根据原项目编写规格。总计 **743 个计分 API、2,705 条计分规格**。项目覆盖密码协议、分布式系统、数据结构等领域。翻译流水线的每个阶段都经过人工审核。这个设置保留了真实项目的共享定义与模块依赖，同时统一了 Lean 4 的评测环境。[论文 §3.3–3.4](https://arxiv.org/html/2608.13522v1#S3.SS3)

但“Lean 能编译”并不意味着基准规格正确。论文给了三种机器可检查的反证路径：

1. **参考实现不满足规格**：证明 $\neg\bigwedge_{S\in\mathcal S}S(\texttt{canonical})$，指向参考实现或翻译错误。
2. **单条规格无解**：对某个 $S$，证明 $\neg\exists\,impl:\texttt{RepoImpl},\ S(impl)$。
3. **规格集互相冲突**：某些规格各自可满足，但不存在一个实现同时满足它们。

附录 F 的 `verdict` 案例把第三种问题说得很直白：Base64 的填充字符 `=` 是十六进制 `0x3D`。一条规格要求分类函数对它返回 `some none`，另一条“拒绝非法字符”的规格却把 `(0x39, 0x41)` 整段划为 `none`；`0x3D` 正好落在其中。于是不存在能同时满足两条规格的实现。修复方法是在拒绝范围中明确排除 `0x3D`。论文报告，审计在发布的 43 个实例中定位并修复了 **38 条有缺陷的规格**，涉及 9 个实例，另有 6 组联合不可满足的规格。[论文 §3.5、附录 F](https://arxiv.org/html/2608.13522v1#S3.SS5)

这里的 insight 是：验证基准自身也有证明义务。否则，代理找不出一份不存在的证明，可能被误判为能力不足。Vero 把“证明目标为假”变成可提交、可检查的证据，而不是只靠人工猜测。

### 分数揭示的真正瓶颈

论文在每个仓库给代理 90 分钟。最强配置 GPT-5.5 (xhigh) 在 code-and-proof 模式完整解决 **27/43**，在 proof-only 模式解决 **25/43**；同一模型的 medium 配置分别只解决 **2/43** 与 **6/43**。xhigh 的逐规格通过率分别达到 **87.3%** 和 **85.8%**。一方面，一个仓库只要剩一条关键规格未证完，仓库仍未完成；另一方面，**只改变思考强度，完整解决数就可以大幅变化**。这是解读 CoCo-Prover 时必须摆在前面的强基线。[论文 §4.2](https://arxiv.org/html/2608.13522v1#S4.SS2)

![Vero 论文图 3：各代理在两种任务模式下的完整仓库解决情况](../assets/papers/vero-results.svg)

*原论文图 3。曲线统计 90 分钟内累计完整解决的仓库；右侧展示不同配置解决了哪些实例。*

难点也并非“跨模块”四个字本身。论文发现，涉及**全局覆盖性**的规格失败率最高，达 **47.1%**；在同一仓库内，使用给定辅助定义、重复调用同一 API 的规格，失败率分别高出 **14.9** 和 **11.7 个百分点**。需要理解多次执行后的不变量、建立可复用引理，才是难处。[论文图 8 与 §4.2](https://arxiv.org/html/2608.13522v1#S4.F8)

附录 H 的 `deposit_sc` 是具体例子：79 条规格跨 `Bits`、`Tree`、`Merkle`、`Contract` 四个模块。要证明“批量 deposit 的折叠结果等于逐个 deposit”，直接对输入列表归纳会卡住；归纳步还需要知道中间状态有效，以及树高、合并函数和默认值没有变。成功证明先提出一个**更强的合取归纳命题**，同时携带这些事实，再让每层模块的引理依次调用。其 code-and-proof 提交包含 99 条辅助定理和 6,052 行非空证明代码。真正的创造性在于选对归纳命题。这个案例也提醒我们：强通用代理在高思考强度下已经能自行组织大型引理库；CoCo-Prover 不能仅凭“会规划引理”证明自己超越了它。[论文附录 H.2](https://arxiv.org/html/2608.13522v1#A8.SS2)

## 二、CoCo-Prover：把证明搜索变成受成本约束的调度

Vero 展示了大量相互依赖、难度不一的目标。CoCo-Prover 的出发点是：若所有目标都调用同一种昂贵模型、使用同样长的搜索预算，简单目标被过度计算，难题又缺少持续的结构化积累。论文将选择拆成两个问题：**接下来做哪些目标**，以及**为这些目标购买哪一种证明动作及预算**。成本按实际货币支出计，因为输入、缓存和输出 token 的价格不同。[论文 §3.1](https://arxiv.org/html/2610.09681v1#S3.SS1)

### 两层证明图分别保存什么

第一层是**声明之间的依赖 DAG**：目标定理与辅助引理都是节点。若证明 $v$ 使用 $u$，就有边 $u\to v$。一个引理可以被多个目标复用，也可能仍是待证明的临时假设；系统记录它是稳定、暂定还是废弃。第二层是**单个声明内部的 AND/OR 证明超图**：一个策略步骤可能生成多个子目标，这些子目标必须全部关闭（AND）；同一个目标又可能尝试不同的证明路线（OR）。Lean 已检查的步骤成为图里的已验证边。[论文图 2](https://arxiv.org/html/2610.09681v1#S3.F2)

![CoCo-Prover 论文图 2：引理依赖 DAG 与单一定理内部的 AND/OR 证明图](../assets/papers/coco-proof-graphs.svg)

*原论文图 2。左图表示跨声明复用，右图表示单个证明步骤如何展开为子目标。*

图的作用不只是画出搜索过程。它告诉系统哪些目标依赖已经就绪、哪些已证明成果能保留、一个临时引理失败时该撤销哪些后继。调度器以类似拓扑遍历的方式暴露当前可处理的前沿 $\mathcal F_t$，不需要一次模型调用来猜依赖顺序；路由器再决定对前沿的哪一组目标花钱。形式上，动作是 $c_t=(G_t,o_t,\theta_t)$：$G_t$ 是目标组，$o_t$ 是专家代理，$\theta_t$ 是推理强度或迭代上限。[论文 §3.1](https://arxiv.org/html/2610.09681v1#S3.SS1)

论文用 $\mathbf 1[\mathrm{solve}]-\lambda C$ 表示整体目标：完成证明的收益减去成本惩罚。这个式子并非实现里精确求解的动态规划；它是路由策略的规范性目标。关键是**看全局剩余任务的预计成本**：某条共享引理单独看很贵，但若五个目标都要重新发现它，先证明一次反而更便宜。若临时引理失败，下游已花的钱会成为回滚风险；依赖图也让这一风险可计算。[论文 §3.1、附录 B.5](https://arxiv.org/html/2610.09681v1#S3.SS1)

### 一轮运行如何进行

![CoCo-Prover 论文图 3：调度器、路由器、四种专家代理及 Lean 检查器](../assets/papers/coco-workflow.svg)

*原论文图 3。调度器给出依赖已就绪的目标；路由器决定动作；代理把检查结果写回图和共享记忆。*

系统的循环可以按论文图 3 理解：

1. **符号调度**读取两层图，找出尚未解决、依赖已就绪的 Lean 目标。路由器用语义聚类把相近目标放在一起，并读取局部证明状态、失败记录、成本账本。
2. **路由决策**选择目标组、专家、推理强度和工作预算。初始原则是：如果两种动作对最终可证明性的预期相近，选完成整个任务预计更便宜的一种。规则可根据之后的检查反馈更新。
3. **执行与反馈**由专家代理调用 Lean，成功的步骤、产生的子目标、诊断和实际成本写回图。测试能排除错误的候选引理，但不能代替 Lean 内核证明。

四类专家各有职责：**Deterministic Automation** 先尝试无需模型的规则化策略；**Proof Writer** 写 Lean 证明并迭代修复，预算耗尽仍保存已经验证的部分；**Lemma Planner** 把阻碍证明的事实提升成有类型、能明确服务于目标的辅助引理，经过语法、无环性和反例检查后加入依赖图；**Recovery Reviewer** 判断分支是否可能为假或路线过贵，必要时退回最近的安全状态。一次失败只撤销受它影响的后继，不必重做全部已验证工作。[论文 §3.2](https://arxiv.org/html/2610.09681v1#S3.SS2)

### 案例一：一个字符串定理为什么要九条引理

附录 D.1 的 CLEVER `prob_15` 要实现 `string_sequence`：将 `0` 到 `n` 的十进制表示用空格连接。实现自然写成 `" ".intercalate ((List.range (n+1)).map Nat.repr)`；规格却用 `splitOn " "` 重新解析输出，并要求第 $i$ 段等于 `i.repr`。人眼看到“拼接再切开”，Lean 需要知道每段没有空格、`intercalate` 与 `splitOn` 相互抵消。更麻烦的是 Lean 的字符串 API 下方涉及字符列表、私有累加器、UTF-8 字节位置扫描，并没有现成的一条总定理。[论文附录 D.1.1](https://arxiv.org/html/2610.09681v1#A4.SS1.SSS1)

CoCo-Prover 沿抽象层逐步立引理：先把规格化成拼接后切分的目标；再证明自然数表示不含空格；然后桥接字符串与字符列表；最后下降到字节扫描和偏移量性质。运行共 **8 轮控制循环、18 次路由调用**，得到 **9 条辅助引理**，无回滚，花费 **$2.36**。同一模型和价格下，两个成功的基线分别花费 **$8.67**、**$10.74**；另一个基线花费 **$5.48** 仍未完成。论文指出，成功基线发现的数学事实大致相似，差距主要来自上下文重复发送和证明进度是否持久保存。[论文附录 D.1.2–D.1.5](https://arxiv.org/html/2610.09681v1#A4.SS1.SSS2)

![CoCo-Prover 论文图 6：字符串案例的引理依赖图](../assets/papers/coco-case-lemmas.svg)

*原论文图 6。每条边从辅助引理指向使用它的声明；图的深度对应从规格下降到 UTF-8 扫描的层级。*

这个案例说明，“发现缺少一个事实”与“把事实变成可管理的证明任务”之间有很大距离。Lemma Planner 负责后一步，两层图确保已证事实不会在下一轮模型调用中丢失。

但论文也说，两个成功基线最后找到的引理结构与 CoCo-Prover 接近。该案例最直接支持的结论是**在 GPT-5.6-Terra 和这一道题上，结构化上下文节省了模型调用成本**；它没有测更强模型是否能用更少轮次、更少上下文完成同一证明。并且 CoCo-Prover 用时 2,816 秒，Codex 用时 2,550 秒：少花美元不等于更快。[论文附录 D.1.2–D.1.5](https://arxiv.org/html/2610.09681v1#A4.SS1.SSS2)

### 案例二：56 条区间规格如何共享一座证明库

附录 D.2 的 Vero `prob_14` 是半开整数区间 $[lo,hi)$ 构成的集合库。它有 `overlaps`、`mergeOverlaps`、`chop` 三组操作，共 **56 条规格**。核心规格包括：合并前后覆盖的整数相同；合并结果严格有序且不重叠；相同覆盖集合对应唯一规范形式；输入排列变化不应改变规范结果。[论文附录 D.2.1](https://arxiv.org/html/2610.09681v1#A4.SS2.SSS1)

证明难在实现不是单层函数：`mergeOverlaps` 先用 `insertByLo`/`sortByLo` 排序，再用 `coalesce` 合并。插入用结构递归，排序用折叠，合并则在改变列表头之后做良基递归。若直接展开所有定义，目标会膨胀。成功路线是先证明一次插入保持覆盖，再提升到排序；证明排序结果有序且非空；最后对合并函数使用与其递归方式相匹配的函数归纳。上层的唯一性、排列不变性再从“覆盖不变 + 规范形”推出，不重新展开排序算法。[论文附录 D.2.3–D.2.5](https://arxiv.org/html/2610.09681v1#A4.SS2.SSS3)

该运行完成 **56/56 条目标**，最终文件含 **55 条被实际使用的辅助引理**，依赖链最深 6 层；同一底座模型的编码代理基线只完成 **5/56**。`sortByLo_pairwise_lo` 和 `sortByLo_output_nonempty` 两条引理分别被 31 和 28 条目标间接依赖。运行也进行了 52 次有理由的回滚，常见原因是自动化过早展开递归定义；系统退回安全节点，改用归纳或现成引理。[论文附录 D.2.2–D.2.6](https://arxiv.org/html/2610.09681v1#A4.SS2.SSS2)

这里最重要的 insight 是**跨目标复用**：目标定理一旦证明，也能像辅助引理一样成为其他目标的依赖。这样，仓库中的 56 条规格不是 56 次相互隔离的搜索，而是一座逐层增长的证明库。

但这仍是一个**Terra 对 Terra**的案例：基线只完成 5/56，说明在这个底座、时限与实现下，持久证明图非常有用；它没有回答 GPT-5.5 (xhigh) 这样的强配置在同一题上能完成多少。Vero 原论文中的 `deposit_sc` 已证明强代理能够构造更深的大型引理库，所以“弱基线缺少依赖图”不能直接推出“强模型也离不开这套调度”。

## 三、效果到底有多大：按证据强弱分层

### 同论文、同底座：方法确有收益

CoCo-Prover 在 CLEVER、VERINA、AlgoVeri 三个函数级基准及 NTP4VC、Vero 两个仓库级基准上测试。它不是“只在 Terra 上测”：底座还有 Gemini-3.5-Flash 与 DeepSeek-V4-Flash。在 Vero 的 proof-only 任务上，三种底座各自的 CoCo-Prover / 编码代理完整解决数分别为 **23/1、26/3、6/0**（分母均为 43）。这些是同论文、同底座、同任务上相当大的差距，不能抹掉。[CoCo-Prover 表 1、§4](https://arxiv.org/html/2610.09681v1#S4.T1)

成本比较的口径也有合理处：论文表 2 对每个基线只比较**双方都成功**的题目，避免把失败后少花钱当成效率优势。在九个函数级“基准 × 模型”组合上，CoCo-Prover 在共同成功题目上的模型账单均较低。但这个统计刻画的是**成功交集里的模型支出**，不是全部题目的端到端成本；论文也说明，Lean 检查、检索、向量嵌入等本地算力不计入美元成本。CoCo-Prover 在 Terra 与 Gemini 下的平均墙钟时间反而更长。[CoCo-Prover 表 2、附录 C.1–C.2、F](https://arxiv.org/html/2610.09681v1#A3.SS1)

### 与强模型相比：论文没有完成关键对照

| Vero proof-only 设置 | 完整解决 | 每题上限 | 能说明什么 |
| --- | ---: | --- | --- |
| Vero 原论文：Codex + GPT-5.5 medium | 6/43 | 90 分钟 | 思考强度较低时的通用代理表现 |
| Vero 原论文：Codex + GPT-5.5 xhigh | 25/43 | 90 分钟 | 同一模型提高思考强度后的表现 |
| CoCo-Prover：GPT-5.6-Terra | 23/43 | 8 小时、$60 | 该底座与该方法组合的表现 |
| CoCo-Prover：Gemini-3.5-Flash | 26/43 | 8 小时、$60 | 另一底座与该方法组合的表现 |

表中最值得注意的是两个事实。第一，**CoCo-Prover + Terra 的 23/43 没有超过 GPT-5.5 (xhigh) 的 25/43**；Gemini 组合的 26/43 则多 1 题，所以不能笼统说“CoCo-Prover 所有结果都没超过 5.5 xhigh”。第二，两篇论文使用不同模型、代理版本、价格与时间上限：这张表只能指出**缺失的强基线与可能的能力替代效应**，不能据此宣称 xhigh 在同条件下必然优于 CoCo-Prover。[Vero §4.1–4.2](https://arxiv.org/html/2608.13522v1#S4.SS1)、[CoCo-Prover §4、附录 C.1](https://arxiv.org/html/2610.09681v1#A3.SS1)

更关键的是，CoCo-Prover 的 OpenAI 评测底座只有 GPT-5.6-Terra；GPT-5.6-Sol 的 high 配置只用于预先生成 CLEVER 和 AlgoVeri 的参考实现，并非被评测的证明器。方法章节把每次调用的思考强度写进配置 $\theta$，字符串案例也说规划用 high-thinking、Proof Writer 用 low-thinking；但论文没有给出覆盖全部任务的**思考强度逐次设置与强度扫描结果**，无法像 Vero 的 medium/xhigh 对照那样分离“路由方法增益”与“更多推理计算的增益”。[CoCo-Prover §3.2、§4、附录 C.1、D.1.3](https://arxiv.org/html/2610.09681v1#S3.SS2)

### 消融证明了组件有用，却没有证明增益不会消失

用 Gemini-3.5-Flash 做的 30 题消融中，去掉路由器，总成本上升 **39.9%**；去掉引理规划器，总成本上升 **41.6%**，完成题数从 30 降到 27。这说明在**固定这一底座、这一题集**时，组件确实发挥作用。消融没有覆盖 Vero，也没有把“更强模型、更高思考强度的简单代理”纳入同一实验矩阵。因此无法从组件消融推断：随着模型升级，CoCo-Prover 对简单代理的绝对优势仍会保持。[CoCo-Prover §4.2](https://arxiv.org/html/2610.09681v1#S4.SS2)

## 四、真正需要的实验：方法与模型能力的交叉对照

要检验“方法会被更强模型和更高思考强度吞噬”，应在**同一批 Vero proof-only 实例**上交叉运行两种框架：普通编码代理与 CoCo-Prover；每种框架分别使用 Terra、强模型，以及每个模型可比的 medium/high/xhigh 等推理配置。固定 Lean 版本、定理原文、检索工具、审查规则和时间/美元上限，报告每个格子的完整解决数、逐题成功集合、模型账单、总墙钟时间与运行方差。尤其要看强模型解决的是不是 CoCo-Prover 独有的那批题，而不能只比较总数。

这样的实验会区分三种可能：一是强模型下 CoCo-Prover 仍以更低成本解决更多仓库，说明调度与模型能力互补；二是成功率差距收缩，但成本仍有优势，说明方法主要是效率工程；三是强模型的简单代理同时追平成功率和成本，说明当前方法收益主要来自补足较弱底座的组织能力。现有论文**支持同底座的工程收益**，却还不能判定哪一种随模型升级出现。

Vero 给出了问题和强思考基线；CoCo-Prover 给出了持久证明图、共享引理与按目标调度的好方法。把两篇连起来读，最有价值的结论不是“方法无效”，而是：**当强代理已经能自发建立证明库时，新的证明框架必须在匹配模型、思考强度和预算的实验里证明额外价值。**
